## 1. Project architecture summary

- **What it is:** offline-first, single-page, client-side Arabic (RTL) mobile-shop management app. No server, no framework, no database server.
- **Runtime:** vanilla HTML/CSS/JS opened directly in a browser (also shared as a single file via WhatsApp/email).
- **Storage:** browser `localStorage` (~5 MB limit). Daily partitions `mshop_d_YYYY-MM-DD`, plus static keys (`mshop_cfg`, `mshop_inventory`, `mshop_notes`, `mshop_notifs`, `mshop_trash`, `mshop_calc_hist`, `mshop_repair_parts`, `mshop_fault_types`, `mshop_emergency_backup`, `mshop_last_backup`, `mshop_backup_history_log`).
- **Layers (per PROJECT_HANDOFF.md):** UI (`accessories/cash/usedPhones/expenses/software/phones/repair/...`) → Repository (`db_integration.js`) → Mappers (`entity_mappers.js`) → Provider/Storage API (`storage.js`) → `localStorage`.
- **Security model:** 4-digit PIN lock + admin PIN (client-side only), AES-GCM + PBKDF2 encrypted backups (`.mshop`, Web Crypto API). Google Drive sync via a Google Apps Script web-app URL (`GAS_URL` in `app.js`). Supabase sync files exist but are **not wired into the app** (see §3).
- **There is no backend/API, no SQL database, no migration system.** "Database" = `localStorage` key layout + repository/mapper JS. Nothing in Phase 6 applies as destructive schema work; the rule "never delete migrations" is trivially satisfied (there are none).

## 3. Build / run process

1. Edit files under `dev(_extracted)/dev/`.
2. Run `python dev/build.py` from the project root → writes `dist/index.html` (single file: CSS inlined, all JS concatenated in `index.html` script-tag order).
3. Open `dist/index.html` in a browser (production) or `dev/index.html` (dev, individual files). No server, no bundler, no compile step.
4. Tests: `dev/tests/*.js` are standalone scripts (with `dom-stub.js`); no test runner config found — invocation to be confirmed in Phase 9 (`node dev/tests/<file>` candidates).
5. **Not wired into the build:** `sync_supabase_config.js`, `sync_provider_supabase.js`, `sync_auth.js` have NO `<script>` tag in `index.html` and the page loads NO Supabase SDK (no CDN tag, no `import`/`require` of `@supabase/supabase-js` anywhere in `dev`). The installed npm package is therefore currently dead weight for the shipped app. `sync.js` (the Drive-sync + documented-only sync architecture) IS loaded and uses `GAS_URL` defined in `app.js`.

## 4. Deployment process

- Manual: build `dist/index.html` → share file directly (WhatsApp/email) or open locally. No CI/CD, no Dockerfile, no hosting config in this folder.
- Data flows out of the device via: (a) JSON/`.mshop` backup files, (b) `uploadToDrive()` POST of **all** `mshop_*` keys to the hardcoded `GAS_URL`, (c) `downloadFromDrive()` JSONP from the same URL.
- Consequence: every distributed single-file build **carries the `GAS_URL` and any inlined config** with it. Recipients of the file gain the ability to call that Drive endpoint.

## 5. Database / migration structure

- No RDBMS, no migration files, no seed scripts. Schema = `localStorage` key conventions + `db_foundation.js` (documentation only, not runtime) + repository/mapper code.
- `sync_provider_supabase.js` references server tables (`sync_records`, `sync_operations`, `sync_log`, RPC `sync_records_by_entity_pairs`) but is **reference-only / untested against any real project** per its own header — there is no local SQL to protect.
- Rule for later phases: nothing here qualifies as an applied production migration, so there is nothing to squash; still, do not touch `storage.js` key layout or repository adapter maps without a data-migration plan.

## 6. Configuration structure

- Runtime config lives in `localStorage` (`mshop_cfg`: shop name, logo, `passMain`, `passAdmin`, admin timeout). Defaults are hardcoded in `app.js` (`passMain:'1234'`, `passAdmin:'5678'`) with the default PIN hint rendered in `index.html` lock screen.
- Cloud endpoints: Phase 3 moved the GAS endpoint behind a single boundary (`dev_extracted/dev/js/app_config.js` → `APP_CONFIG`, placeholder only, fail-closed when empty). Runtime config otherwise lives in `localStorage` (`mshop_cfg`). No `.env`, no secret manager. The single-file distribution model cannot consume process env at runtime; the boundary is for maintainability/rotation, NOT secrecy (see `docs/SECURITY_CONFIGURATION_PROPOSAL.md` §6).

## 9. Risks

1. **GAS bearer-URL proliferation (HIGH):** every shared HTML copy embeds a live read/write endpoint to shop data. Leakage = data exfiltration/injection without any PIN (PIN is client-side only).
2. **Client-side-only access control (HIGH by design):** PINs, admin gate, profit masking are UI-level; anyone with the file or DevTools bypasses them. Must never be relied on for real secrecy.
3. **Known Issue 2 — encrypted restore drops today's sales (CRITICAL, open):** do NOT run encrypted restores on production data until root-caused. Diagnostic V2 exists but is untested.
4. **5 MB `localStorage` quota + emergency-backup doubling during restore:** near-quota shops risk silent `saveRaw` failure (console/alert only, invisible under restore overlay).
5. **No version control in this folder (MEDIUM):** no `.git/` → no history to leak (good), but also no change tracking, no `.gitignore` protection if the folder is later pushed — pushing as-is would publish the `GAS_URL`.
6. **Supabase publishable key in cleartext (LOW if RLS correct, HIGH if RLS open or if project is someone else's):** owner must confirm the project and its Row-Level Security before any sync goes live.
7. **Unverified Supabase provider code (MEDIUM):** header-marked untested; must stay unloaded until the documented production gate passes.
8. **Dependency drift (LOW):** `package.json` has no scripts/engines and the lockfile is committed; harmless while unused, confusing if left unexplained.

## GAS_URL classification — evidence, not guesses

Question: endpoint only (1), access-bearing secret (2), authorization-in-URL (3), or server-side-controlled (4)?

- **Verified fact:** the ONLY outbound network call in the entire application is `fetch([GAS_URL_REDACTED], {method:'POST', body:<entire localStorage dump>})` (`sync.js:10`); the download path is JSONP `…?callback=…&t=…` (`sync.js:26`). Zero `Authorization` headers, zero tokens/API keys, zero extra auth params anywhere in source (full-tree scan for `Authorization|headers:|apiKey|access_token|authToken` = no hits). Only other external resource is a Google Fonts stylesheet.
- **Verified fact:** the server-side GAS project (`doPost`/`doGet`) is NOT in this repository — its access checks (if any) cannot be inspected from here.
- **Conclusion:** from all repo-side evidence this is **(3) an endpoint with authorization embedded in the URL — a capability-style bearer URL — and must be handled as (2) an access-bearing secret**. Possession of the URL demonstrably permits full shop-data upload and download with no additional credential. Claim (4) (server-side control) is **UNVERIFIABLE** from the repo and must NOT be assumed; the safe posture is weakest-case until the GAS project itself is inspected by its owner.
- **Consequence for "env-var" fixes:** any value the browser needs at runtime (options A/B) remains visible to every file holder and DevTools user — see proposal §6. Moving it is hygiene/rotation-agility, not secrecy.
