# ADR-001: نقطة بيع واحدة تملك صلاحية تعديل المخزون

## الحالة

مقبول بقرار المالك في 2026-09-28.

## السياق

يعمل Windows في البيع دون اتصال، بينما يعمل Android عند الاتصال ويقدم وظائف البيع والإدارة. عند بيع الجهازين من نفس رصيد المخزون، لا تستطيع قاعدة البيانات البعيدة معرفة مبيعات Windows غير المتصلة؛ وقد يُباع نفس IMEI أو آخر كمية مرتين.

## القرار

- توجد صلاحية POS واحدة فعالة لكل المحل.
- Windows هو POS الأساسي ويحتفظ بالملكية أثناء انقطاع الإنترنت؛ لا تنتهي الملكية بسبب timeout أو غياب heartbeat.
- لا ينفذ Android بيعًا أو عملية أخرى تؤثر في رصيد البيع ما لم يملك POS صراحةً.
- نقل الملكية إلى Android يتطلب اتصال الجهازين، إفراغ طابور Windows ومزامنته بنجاح، ثم release صريح من Windows وacquire من Android.
- تحفظ حالة الملكية محليًا وعلى backend، مع سجل مدقق للمستخدم والجهاز ووقت التغيير. قرارات المخزون على كل جهاز تتحقق من الملكية في طبقة Rust/backend، لا من حالة الواجهة فقط.
- لا يُسمح بتسليم تلقائي قسري إذا تعذر الوصول إلى Windows وقد يحتوي على مبيعات غير متزامنة؛ يلزم إجراء استرداد وجرد يقرره المالك ويُسجل كتسوية.

## البدائل التي رُفضت

### السماح بالبيع من الجهازين مع حل التعارض بعد المزامنة

مرفوض لأن البيع المكتمل للعميل لا يمكن التراجع عنه بأمان عند اكتشاف بيع مكرر لاحقًا، خصوصًا للأجهزة ذات IMEI فريد.

### انتهاء قفل POS تلقائيًا بعد غياب heartbeat

مرفوض لأن انقطاع اتصال Windows لا يعني توقفه عن البيع offline؛ انتهاء القفل قد يفعّل Android بينما يستمر Windows في البيع محليًا.

## النتائج

- سلامة المخزون وIMEI لها الأولوية على توفر البيع من Android عند وجود مبيعات Windows غير متزامنة.
- قد يبقى Android ممنوعًا من checkout حتى يعود Windows ويزامن، حتى لو كان Windows غير متاح مؤقتًا.
- يلزم مسار إداري منفصل لمعالجة تعطل Windows نهائيًا، ويتضمن جردًا/تسوية للسجلات غير المؤكدة؛ هذا المسار لا يُنفذ تلقائيًا.
- تحقق قبول إلزامي: بينما Windows مالك POS وغير متصل، يرفض Android عمليات البيع وتعديل المخزون؛ بعد المزامنة والتحرير الصريح، يقبل Android البيع، ويرفض Windows أي checkout جديد ما لم يستعد الملكية.
