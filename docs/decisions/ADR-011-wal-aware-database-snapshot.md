# ADR-011: لقطة قاعدة البيانات وWAL — ما الذي يُنسخ فعلًا

**الحالة:** مقبول (accepted) — قرار المالك 2026-10-07.

**علاقته:** يكمّل `ADR-003` (تنسيق النسخة المشفّرة) ولا ينافسه. `ADR-003` يقرر **ماذا** تكون النسخة المشفّرة؛ هذا الـADR يقرر **كيف** تُلتقط صورة صحيحة من قاعدة SQLite على جهاز Android.

---

## السياق

هذه ليست مشكلة نظرية. حدثت فعليًا خلال شريحة `inventory-procurement` (SP-1)، وتسببت في **توقف بوابة التحقق مرتين**.

### أين يقع ملف قاعدة البيانات فعليًا

`src-tauri/src/lib.rs:72-79` يفتح القاعدة عند:

```rust
let data_dir = app.path().app_local_data_dir()?;
let pool = … db::open(&data_dir.join(DB_FILENAME))   // DB_FILENAME = "shop.db"
```

على Android، `app_local_data_dir()` هو **جذر مجلد بيانات التطبيق**:

```
/data/user/0/com.mshop.system/shop.db
```

**وليس** `databases/shop.db` كما هو شائع في تطبيقات Android. مجلد `databases/` موجود فعلًا لكنه **فارغ تمامًا**. الإجراء الذي كُتب أولًا في محادثة بينوكرة بـ`databases/` كان خاطئًا، ولولا فحص `ls -la` قبل النسخ لإنتاج **ملف فارغ بحجم صفر** يحمل اسم قاعدة البيانات.

### الفرق الجوهري بين قبل الـmigration وبعده

قبل التشغيل على الجهاز، لم يكن هناك أي WAL:

```
shop.db   110592 bytes
```

قاعدة البيانات في وضع WAL، و**لا يوجد ملف `-wal` فيها**، تكون مكتفية بذاتها. فكان نسخ `shop.db` وحده صحيحًا تمامًا.

بعد تنفيذ `0004` و`0005`، تغيّرت الصورة:

```
shop.db       110592 bytes   ← لم يتغيّر إطلاقًا
shop.db-wal   111272 bytes   ← كل عمل الـmigrations هنا
shop.db-shm    32768 bytes
```

`am force-stop` **ليس إغلاقًا نظيفًا** لـSQLite. لا يقوم إلا بالفحص (checkpoint) ويحذف ملف WAL عند إغلاق **آخر اتصال بشكل طبيعي**. القتل القسري يتخطى ذلك، فتبقى إطارات الـmigration المُلتزَمة داخل `shop.db-wal`.

**الدليل القاطع:** بصمة `shop.db` بعد الـmigration مطابقة تمامًا للنسخة الاحتياطية السابقة للـmigration (`7EB36A83…28787C4`).

## الأثر الحقيقي: نسخ `shop.db` وحده الآن يُنتج بيانات قديمة صامتة

هذا هو الخطر الذي لا يترك أثرًا. من ينسخ `shop.db` اليوم يحصل على:

- ملف **سليم تمامًا** يفتح دون خطأ
- `integrity_check` يُرجع `ok`
- لكن `SELECT version FROM _sqlx_migrations` يُرجع `1, 2, 3` — أي **قبل الـmigration**

لا يوجد أي خطأ يمكن رصده. الملف صحيح، لكنه قديم.

### القاعدة

> **لا تُعامل `shop.db` وحده كنسخة صحيحة ما دام ملف WAL موجود.**

النسخة الاحتياطية المقبولة قبل `0005` ( `E:\backups\shop-pre-0005\shop.db` ) **تبقى صالحة**، لأنها أُخذت في لحظة لم يكن فيها WAL، فهي مكتفية بذاتها.

## القرار

### الآلية المعتمدة الآن

لقطة قاعدة جهاز Android تجري **التطبيق متوقفًا**:

1. `adb shell am force-stop com.mshop.system`
2. التأكد أن `adb shell pidof com.mshop.system` فارغ
3. نسخ `shop.db` **و** `shop.db-wal` معًا
4. `shop.db-shm` يُنسخ للاكتمال فقط

### قاعدة الاستعادة

> ضع `shop.db` و`shop.db-wal` معًا، ثم **احذف `shop.db-shm`**، ثم افتح.

`shop.db-shm` هو **فهرس WAL** — مُشتق ومُسرَّع، وليس بيانات. SQLite يعيد بناءه عند الفتح. الاعتماد على نسخة قديمة منه هو مصدر ارتباك على الأقل.

### لماذا quiescence شرط وليس تفصيلًا

ثلاثة نسخ متتابعة ضد **كاتب حي** ليست لقطة في لحظة. فحص checkpoint بين نسخ `shop.db` ونسخ `shop.db-wal` يُصفّر الـWAL، فتُنتج النسخة `db` قديمة مع `wal` فارغ — **فقد بيانات صامت**، وهو بالضبط الخطر الذي وُصف قبل البوابة الأولى.

### لا يوجد اختبار في المشروع يمارس WAL إطلاقًا

```rust
// src-tauri/src/data/db.rs:72-74
let options = SqliteConnectOptions::new()
    .in_memory(true)
    .foreign_keys(true);          // ← لا يوجد journal_mode
```

الـpool الخاص بالاختبارات لا يُصرّح بوضع الدفتر، وSQLite **لا يستطيع** استخدام WAL على `:memory:` فيبقي على دفتر الرجوع.

**النتيجة:** مئة اختبار تكامل تعمل على قاعدة rollback-journal لا على WAL. لا يوجد اختبار في هذا المشروع مارس: نمو WAL، أو checkpointing، أو دورة حياة `-wal`/`-shm`، أو نسخة احتياطية من قاعدة WAL. هذه فجوة تغطية حقيقية، وهي السبب المباشر لأن إجراء خاطئ صمد عشرين بوابة قبل أن يُكتشف.

## البدائل التي رُفضت

### نسخ `shop.db` وحده

مرفوض. صحيح قبل أول WAL، وخاطئ بعده، ويفشل **صامتًا** (§الأثر أعلاه).

### «انسخ الثلاث ملفات دائمًا» كقاعدة عامة

مرفوض كاستراتيجية. صحيح فقط عند غياب كاتب، ولا يعطي لقطة في لحظة مع كاتب حي. هو **إجراء تطبيق متوقف**، لا سياسة نسخ احتياطي. وقد نتج عن إغفاله إدراك خاطئ بأن هذه هي المشكلة الوحيدة.

### `PRAGMA wal_checkpoint(TRUNCATE)` ثم نسخ `shop.db` وحده

مرفوض. يتطلب وجود SQLite **داخل الجهاز** (غير متوفر)، وهو أيضًا كتابة على قاعدة الجهاز، ويمنع الكتّاب.

### الاعتماد على إغلاق نظيف للتطبيق ثم نسخ `shop.db`

مرفوض. غير مضمون عند الانهيار أو قتل العملية أو نفاد البطارية.

### `sqlite3 .backup` على المضيف

مرفوض غير مفيد. الأداة تعمل على **ملف مضيف**، فالنسخة الصحيحة يجب أن تكون موجودة سلفًا —دائرية.

## النتائج

- **نسخ قاعدة الجهاز مؤقتًا مقيد بالتطبيق المتوقف** حتى تتوفر قدرة النسخ عبر الإنترنت (انظر أدناه). مقبول ومرئي، ولا يفترض ضمانًا غير موجود.
- **اكتمال النسخ الاحتياطي والاستعادة يعتمد على قدرة WAL-aware / online backup**. القرار المعماري محسوم: **المخزون لا يملك تنفيذ النسخ الاحتياطي**؛ هذه مسؤولية شريحة `local-backup` ومملوكة لـ`ADR-003`. المتبقي هو **تنفيذ القدرة**، لا إعادة اتخاذ قرار المخزون.
  **NEEDS FOLLOW-UP / DEPENDENCY** — لا `NEEDS decision`.
- **دورة حياة WAL في اختبارات التكامل = UNVERIFIED.** لا تمارسه الاختبارات؛ الدليل على Android حقيقي. اختبارات WAL على قاعدة مدعومة بملف مؤجلة إلى عمل النسخ الاحتياطي والاستعادة المخصص. (قرار المالك 2026-10-07: **لا** تغيير الـpool الآن — مبدأ «لا إعادة هيكلة غير متعلقة».)
- أي إجراء نسخ احتياطي أو استعادة مكتوب مستقبلًا **يجب** أن يشير إلى هذا الـADR.
- قاعدة البيانات على المضيف (`E:\backups\post-0005\`) تحتفظ بمجموعة الثلاثية `-shm` متجاهَلة عمدًا عند الاستعادة.
