# محل الموبايلات — مواصفات النظام المقترح

**الحالة:** مسودة للمراجعة قبل التنفيذ  
**التاريخ:** 2026-09-28  
**أُعيد أساسها (rebaseline):** 2026-10-02 — انظر `docs/decisions/ADR-007-independent-new-system.md`

> **قرار المنتج النهائي (2026-10-02):** النظام الجديد **مستقل تمامًا** ويُصمَّم من أول المبادئ.
> النظام القديم **ليس** مصدرًا للمنطق أو المخطط أو التقارير أو الدلالات المحاسبية، و**ليس** شرطًا معماريًا.
> مادته الأرشيفية باقية في `dev_extracted/` و`archive/` **للأرشفة والتدقيق فقط**، ولا يربطها شيء في هذه المواصفة.

## الهدف

تطوير نظام إنتاجي لإدارة محل موبايلات، يعمل كتطبيق مثبت على Windows وAndroid. يستمر جهاز Windows في البيع وإدارة التشغيل عند انقطاع الإنترنت، بينما يستخدم Android النظام عند الاتصال. تكون الواجهة عربية وRTL، مع صلاحيات واضحة، وبيانات منتجات قابلة للبحث بالباركود وتتبع اختياري للسيريال/IMEI.

## المستخدمون والأدوار

- **المستخدم الأساسي/المدير:** إدارة المنتجات والمخزون، مشاهدة أسعار الجملة والتكلفة والربح، وإدارة المستخدمين والتقارير والإعدادات وملفات العملاء.
- **مستخدم المبيعات:** تسجيل المبيعات والعمليات المسموحة له دون الاطلاع على أسعار الجملة أو إدارة المنتجات؛ يجوز له إدخال بيانات عميل جديدة للفاتورة دون تصفح سجل مشتريات العملاء.
- تُسجل العمليات والتعديلات والإلغاءات بمعرّف المستخدم المنفذ.
- إيقاف المنتج أو أرشفته يحافظ على ارتباطه بالفواتير وحركات المخزون السابقة؛ لا يُحذف سجل تاريخي نهائيًا من تدفق الاستخدام العادي.

## خريطة القدرات وحدود الوحدات

| المعرّف | المسؤولية | يعتمد على |
|---|---|---|
| `platform-data` | تطبيق Windows/Android، قاعدة البيانات المحلية، الإصدارات والترحيلات | — |
| `identity-access` | الحسابات والأدوار والصلاحيات وسجل التدقيق | `platform-data` |
| `catalog-media` | المنتجات والتصنيفات والباركود وطباعته وIMEI/Serial والصورة المحلية — **ملاحظة 2026-10-07:** إسناد التصنيفات لهذه الشريحة مُلغى جزئيًا؛ قرار المالك D2 عرّف «القسم» على أنه **تصنيف المنتجات**، وأصبح جزءًا من شريحة `inventory-procurement` كجدول `departments`. المرجع: `docs/decisions/ADR-012-inventory-schema-foundation.md` | `platform-data`, `identity-access` |
| `inventory-procurement` | سجل المخزون والجرد واستلام توريد مبسط باسم المورد والكمية وتكلفة الوحدة؛ لا أوامر شراء أو مستحقات موردين في الإصدار الأول | `catalog-media`, `identity-access` |
| `customer-records` | ملف عميل بسيط وربطه بالفاتورة/الصيانة/IMEI والضمان؛ الأجل والتقسيط خارج النطاق | `platform-data`, `identity-access` |
| `pos-sales` | البيع والمدفوعات والمرتجعات والإلغاء | `catalog-media`, `inventory-procurement`, `identity-access`, `customer-records` |
| `cash-reconciliation` | حركات الكاش وفتح/إغلاق الوردية ومطابقة العهدة | `pos-sales`, `identity-access` |
| `shop-operations` | الصيانة والمصروفات وسجل التدقيق التشغيلي | `platform-data`, `identity-access`, `inventory-procurement`, `customer-records` |
| `local-backup` | لقطات نسخ احتياطي/استعادة تلقائية ونسخ البيانات والصور محليًا | كل وحدات البيانات |
| `reports` | مؤشرات وتقارير مبنية على المعاملات، بتعريفات مستقلة عن أي نظام سابق | `pos-sales`, `inventory-procurement`, `cash-reconciliation`, `shop-operations` |

> **تعريفات مؤشرات التقارير غير محسومة بعد.** صيغ `Total Sales` و`Net Profit` وغيرها تُعدّ قرار منتج مستقلًا في مواصفة مستقلة لاحقة. لا تُشتق من تقرير قديم ولا تُستنسخ من صيغة سابقة، ولا تُملأ بالمحاكاة.

**ترتيب البناء المقترح:** `platform-data` → `identity-access` → `catalog-media` و`customer-records` → `inventory-procurement` → `pos-sales` → `cash-reconciliation` و`shop-operations` → `local-backup` و`reports`. تُبنى واجهات المزامنة والنسخ الاحتياطي في الأساس مبكرًا، ثم تُربط بالكيانات عبر شرائح كاملة.

## شكل التطبيق والتقنيات المعتمدة

- تطبيق مثبت مستقل على Windows وAndroid، وليس تشغيلًا يطلب من المستخدم فتح المتصفح.
- `Tauri 2` **معتمد بإصدار `2.12.0`**؛ يستخدم WebView داخليًا في نافذة التطبيق. الإصدارات مثبّتة صراحة: `SQLx 0.9.0`، و`Rust 1.98.1` مثبَّت بدقّة عبر `rust-toolchain.toml` مع `Cargo.lock` مُولَّد وملتزم به. ترقيات major/minor التلقائية غير مسموحة. مرجع القرار: `docs/decisions/ADR-008-v1-local-first-platform-scope.md`.
- **لا تُكشف واجهة SQL عامة للـWebView.** إضافة Tauri SQL توفر `execute/select` مباشرة للواجهة، ولا تعرض أمرًا لمعاملة متعددة الاستعلامات؛ لذلك لا تُعتمد كواجهة بيانات إنتاجية. مرجع المصدر: <https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/sql/src/commands.rs> و<https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/sql/src/wrapper.rs>.
- طبقة البيانات: `SQLx 0.9.0` داخل Rust مع أوامر Tauri محددة تتحقق من الدور وتنفذ الاستعلامات. التنفيذ يقع تحت `src-tauri/src/data/repositories/` خلف تجريد المستودعات. توثق `SQLx Pool::begin` بدء معاملة و`Transaction` commit/rollback: <https://docs.rs/sqlx/latest/sqlx/struct.Pool.html#method.begin> و<https://docs.rs/sqlx/latest/sqlx/struct.Transaction.html>.
- الواجهة **Vue** مع **TypeScript في وضع strict** — قرار معتمد، وليس مرشحًا. الواجهة مشتركة قدر الإمكان بين المنصتين. إصدار Tauri غير المثبَّت `tauri = 2` في الـspike ليس إصدار المنتج؛ الـspike دليل مرجعي فقط (`D:\_spikes\tauri-spike`).
- **لا يوجد backend في V1.** لا خادم مركزي ولا قاعدة بيانات سحابية ولا مزامنة تلقائية. كل جهاز يعمل على قاعدة SQLite محلية. `Supabase` **لم يُختر**: الاعتماد `@supabase/supabase-js` **غير موجود في المشروع**، ولا يُقدَّم أي استخدام منه. معمارية المزامنة المستقبلية مؤجَّلة إلى مرحلة منفصلة؛ انظر ADR-008.

### حد الثقة والصلاحيات

- الواجهة لا تحمل بيانات اعتماد قاعدة البيانات ولا تستدعي SQL خامًا. كل قراءة/كتابة تمر عبر أمر Rust مسمى ومتحقق من هوية الجلسة ودورها.
- أمر البيع يلتقط تكلفة البيع كسجل تاريخي، ويتحقق من الرصيد والسيريال، ثم يحفظ الفاتورة والأسطر وحركة المخزون داخل معاملة SQLx واحدة؛ فشل أي خطوة يلغي العملية كلها.
- سعر الجملة لا يرجع في نتائج أوامر دور المبيعات. حماية ملف قاعدة البيانات من مستخدم يملك صلاحيات نظام التشغيل نفسه حدّ ثقة منفصل؛ يُحدد في نموذج التهديد، ولا يُوعد بمنع مسؤول الجهاز من فحص البيانات دون تشفير/فصل حسابات مناسب.
- **مستوى الحماية المعتمد:** منع ظهور سعر الجملة واستخدامه عبر التطبيق لمستخدم المبيعات؛ لا يُشترط تشفير ملف قاعدة البيانات ضد من يملك وصولًا مباشرًا لملفات Windows أو صلاحيات مسؤول. لا يُدّعى أن صلاحيات التطبيق تمنع قراءة ملف SQLite مباشرة؛ تشفير النسخة الاحتياطية قرار منفصل.
- العملة هي **`EGP` (الجنيه المصري)**، والوحدة الصغرى هي **القرش (`piastre`)** بمنفذة **`2` خانات عشرية**. المال يُخزن كعدد صحيح بوحدة القرش (`amount_minor`)، لا `REAL` ولا `f64`. مثال: `100.50 EGP` تُخزَّن `10050`. **سياسة التقريب تبقى مفتوحة** ولا تُحسم في هذه الوثيقة. تعبر مبالغ Rust↔WebView كسلاسل أعداد صحيحة أو نوع يضمن عدم فقدان الدقة؛ تُحوَّل الواجهة للقيمة المعروضة ويُختبر round-trip. المرجع: `docs/decisions/ADR-010-currency-egp-and-minor-unit.md`.

## معمارية الطبقات وهيكل المشروع المعتمد

الهيكل **معتمد** لا مبدئي، ومسجَّل في `docs/decisions/ADR-008-v1-local-first-platform-scope.md`.

**مسار التدفق:**

```text
Vue  →  Tauri Commands  →  Services / Use Cases  →  Domain  →  Repositories  →  SQLite
```

**الواجهة (Vue + TypeScript strict):**

```text
src/                       واجهة Vue — عرض وتفاعل وحالة واجهة محلية فقط
```

**الجزء الأصلي (Rust):**

```text
src-tauri/src/
├── domain/                 قواعد العمل وأنواع المجال — لا تعرف Tauri ولا SQLx ولا SQLite ولا المنصة
├── services/               تنسيق التطبيق وحالات الاستخدام
├── data/
│   ├── repositories/       تجريد الاستمرارية — هنا تنفيذ SQLx و SQLite
│   └── migrations/         ترحيلات SQLite
├── commands/               حدود النقل/الواجهة البرمجية فقط، بلا منطق عمل
└── lib.rs
```

**الاختبارات:**

```text
tests/unit/                 اختبارات منطق النطاق (بلا Tauri ولا SQLite)
tests/integration/          SQLite والمعاملات والترحيلات والنسخ والاستعادة
tests/device/               سيناريوهات Windows وAndroid والأجهزة الطرفية
docs/superpowers/           المواصفات والخطط وقرارات التصميم الجديدة
archive/legacy-project/     وثائق النظام السابق المؤرشفة — خارج المعمارية
```

**قواعد الطبقات:**

- النطاق لا يعتمد على Tauri ولا SQLx ولا SQLite ولا Android ولا Windows.
- الأوامر حدود نقل فقط؛ منطق العمل في `services/` و`domain/`.
- المستودعات تعزل الاستمرارية؛ تنفيذ SQLite/SQLx يبقى تحتها.
- الواجهة لا تمسك بيانات اعتماد قاعدة البيانات ولا تنفّذ SQL.
- **تجنّب طقوس Clean Architecture الزائدة** — لا واجهات أو مصانع أو حاويات حقن بلا سبب ملموس.

### الشروط التي تحفظ إمكانية المزامنة لاحقًا

قيود معمارية فقط، **ولا تُبنى المزامنة في V1**:

1. معرّفات نطاق ثابتة لا تُشتق من موقع التخزين ولا من عدّاد لكل جهاز.
2. حدود واضحة بين النطاق والتطبيق والاستمرارية.
3. تجريد المستودعات.
4. طوابع زمنية وبيانات وصفية حيث يقتضيها النطاق طبيعيًا.
5. النطاق لا يعتمد على SQLite.
6. النطاق لا يعتمد على الشبكة أو النقل.

> صُمّم V1 بحيث تصبح المزامنة ممكنة لاحقًا، **دون بناء المزامنة في V1**.

### نطاق V1 ومنصّتاه

**Android وWindows كلاهما نقطة بيع كاملة في V1**، لكل جهاز قاعدة SQLite محلية خاصة به.
لا مزامنة تلقائية، ولا خادم مركزي، ولا قاعدة بيانات سحابية، ولا محرك حل تعارض، ولا Sync Engine في V1.
معمارية المزامنة المستقبلية مؤجَّلة إلى مرحلة منفصلة — انظر ADR-008 و`ADR-001` (مُلغى في نطاق V1).


## أسلوب الكود المقترح

- أسماء الأنواع والواجهات والحقول البرمجية بالإنجليزية؛ نصوص المستخدم في ملفات رسائل عربية وRTL بدل بعثرتها في منطق المجال.
- منطق المجال مستقل عن مكونات الواجهة وقاعدة SQLite؛ الوصول للبيانات عبر مستودعات/خدمات واضحة.
- TypeScript في **وضع strict** مع Vue. لا تُخفَّف صرامة TypeScript بسبب أي كود قائم في المستقبل.
- معاملات البيع والمخزون تُنفذ كوحدة ذرية؛ لا تُحسب الأرصدة من واجهة أو من قيم قابلة للتعديل يدويًا دون سجل حركة.
- تجنب الحالة العامة القابلة للتغيير؛ لا تُنقل حالة عبر متغيرات عامة أو أنماط مشتركة بلا مبرر مكتوب واختبارات.

## استراتيجية الاختبار

- **وحدات:** صلاحيات الأدوار، حساب الإجمالي/التكلفة، قواعد الباركود والسيريال، ودورة حالات الفاتورة.
- **تكامل:** قيود SQLite ومعاملاتها وترحيلاتها؛ دفتر المخزون؛ ذرّية البيع؛ تصدير واستيراد النسخة والصور. **لا اختبارات outbox/cursor/idempotency للمزامنة** — المزامنة خارج نطاق V1 (ADR-008).
- **أجهزة:** تثبيت وتشغيل Windows وAndroid، انقطاع الشبكة، الكاميرا، قارئ الباركود، والطابعة المستهدفة.
- **ذرية مالية:** فشل متعمد بعد حفظ سطر الفاتورة وقبل حركة المخزون يجب أن يترك قاعدة البيانات دون فاتورة/خصم جزئي؛ اختبار حقيقي على SQLite/SQLx وليس mock.
- **دقة نقدية:** اختبارات حدود تتحقق من تخزين المال كعدد صحيح ومن عدم تمريره عبر `REAL`/`f64` في قاعدة البيانات.
- **قبول:** مسارات manager/sales على كل من Windows وAndroid؛ بيع offline على كل جهاز؛ وكل device يعمل على قاعدة SQLite محلية مستقلة.
- لا يوجد test runner أو build script للتطبيق الجديد بعد؛ تحدد الأوامر الدقيقة ضمن تجربة Tauri، وتُوثق في README الجديد قبل أول شريحة إنتاجية.

## حدود العمل

- **دائمًا:** الحفاظ على نسخة المصدر القديمة؛ الاختبار على نسخ بيانات؛ ترحيلات versioned؛ تدقيق كل عملية حساسة؛ عدم إسقاط معاملات مالية بصمت.
- **تتطلب موافقة:** نطاق المشتريات؛ تشفير قاعدة البيانات المحلية؛ أي تغيير في الأدوار أو إظهار التكلفة؛ وكل قرار يخص المزامنة المستقبلية (خارج نطاق V1).
- **ممنوع:** استبدال بيانات المستخدم الأصلية مباشرة؛ حذف تاريخ منتج مرتبط بعمليات؛ تضمين أسرار خدمة في تطبيق العميل؛ بناء مزامنة أو خادم أو قاعدة بيانات سحابية في V1؛ إضافة اعتمادية على Supabase؛ واعتماد حل تعارض يمحو فاتورة أو حركة مخزون بلا مراجعة.
- لا يُعتمد على واجهة JavaScript أو إضافة SQL ذات وصول خام كحد للصلاحيات؛ طبقة Rust هي نقطة الوصول الوحيدة لبيانات التطبيق.

## التشغيل دون اتصال ونطاق V1

**النطاق المعتمد في V1 (ADR-008):**

- **Android = نقطة بيع كاملة.** **Windows = نقطة بيع كاملة.** كلاهما عميل POS كامل في الإصدار الأول.
- **لكل جهاز قاعدة SQLite محلية خاصة به.** لا قاعدة بيانات مشتركة.
- **لا مزامنة تلقائية في V1.** لا خادم مركزي، ولا قاعدة بيانات سحابية، ولا محرك حل تعارض، ولا Sync Engine.
- **معمارية المزامنة المستقبلية مؤجَّلة** إلى مرحلة منفصلة بعد اكتمال نقطة البيع المحلية والتحقق منها. لا تُصمَّم هنا.

**سلوك كل جهاز:**

- يواصل **كل** جهاز تسجيل المبيعات والعمل الأساسي دون اتصال بالإنترنت. لا يقترن ذلك بكونه POS أساسيًا أو تابعًا.
- لا يوجد قفل ملكية عبر الأجهزة. كل جهاز مستقل على بياناته المحلية.
- لا يُرفض أي بيع بسبب حالة جهاز آخر.

**ماذا لم يُحسم (لا يُقرَّر هنا):**

- إن كانت بيانات أي جهاز ستنتقل إلى جهاز آخر، وكيف، ومتى — قرار **مؤجَّل**.
- أي سياسة لتعارض البيانات بين الأجهزة — **غير موجودة في V1** ولا تُصمَّم.

**ملاحظة تاريخية:** كان هذا القسم يصف «ملكية نقطة بيع واحدة» ونقل ملكية عبر الأجهزة. تلك الآليات تنتمي إلى مرحلة المزامنة المستقبلية. قرار ADR-001 القائم على مزامنة عبر الأجهزة **مُلغى في نطاق V1**؛ نصّه الأصلي محفوظ كسجل تاريخي. انظر docs/decisions/ADR-001-single-pos-ownership.md وADR-008.


- سطر الفاتورة يحفظ لقطة وصف المنتج/الباركود والسعر والتكلفة والربح وقت العملية؛ تعديل سعر الشراء في كتالوج المنتج لا يعيد كتابة ربح عملية قديمة.
- **قرار معتمد في ADR-002:** متوسط تكلفة مرجح متحرك للأصناف الكمية، وتكلفة شراء فعلية لكل وحدة IMEI/Serial. تحفظ كل فاتورة بيع التكلفة المختارة كـsnapshot. التفاصيل: `docs/decisions/ADR-002-inventory-costing.md`.
- **الرصيد الافتتاحي:** النظام الجديد يبدأ بقاعدة بيانات فارغة. أي صنف تُتابَع كميته يحتاج رصيدًا افتتاحيًا يدخله المستخدم قبل أول بيع؛ لا تُخترع كميات ولا يُشتق رصيد من أي مصدر آخر. الصنف الذي لا تُتابَع كميته (قطعة تُباع مرة واحدة) يُسجَّل بيعه كحركة دون رصيد مخزون. تصنيف كل صنف على هذا الأساس قرار يُوثَّق في مواصفة الكتالوج.
- **الباركود:** حقل مستقل في النظام الجديد، يُنشأ للمنتج ولا يُستنتج من أي معرّف آخر. إنشاء الباركود وملصقاته وظيفة جديدة بالكامل.
- **نسب السجلات:** كل عملية تُنسب إلى المستخدم المنفذ عبر أمر Rust متحقق منه. النموذج الجديد لا يحتوي استيرادًا ولا حالة "مستخدم غير معروف".
- **ربط العميل:** لا يُدمج أي اسمين متشابهين في سجل عميل واحد. الربط بالعميل اختياري ويحدث بأمر صريح؛ وإلا يبقى الاسمSnapshot نصيًا على العملية نفسها.
- **نطاق عميل معتمد:** اسم ورقم تواصل واحد اختياريان، وربط اختياري بالفاتورة/الصيانة/IMEI وسجل فترة الضمان. تسجل بداية ونهاية الضمان للجهاز/البيع؛ لا نظام مطالبات في الإصدار الأول. لا عنوان أو رقم قومي دون حاجة معلنة؛ المدير يشاهد التاريخ، ومستخدم المبيعات لا يتصفح سجل الشراء.

### تعريفات مؤشرات التقارير المالية

**لا توجد تعريفات معتمدة بعد.** صيغ `Total Sales` و`Net Profit` ومؤشرات التقارير الأخرى تُعدّ قرارًا منتجيًا مستقلًا في مواصفة تقارير لاحقة، تُكتب من أول المبادئ.

- لا تُشتق أي صيغة من تقرير سابق، ولا تُستنسخ من محرك حساب سابق، ولا تُملأ بمحاكاة أرقام قديمة.
- لا تُستخدم أرقام النظام القديم مرجعًا للمقارنة أو لمعايرة أي مؤشر.
- كل مؤشر يُعرَّف باسم صريح ودلالة مكتوبة؛ لا يُعاد استخدام اسم Carry دلالة مختلفة بصمت.
- أي مؤشر جديد أو تغيير في صيغة موجود يُعتمد كـmetric جديد باسم جديد.

## المنتجات والصور والباركود

- لكل منتج صورة رئيسية واحدة؛ يختارها المستخدم من ملف أو يصورها بكاميرا Android.
- تحفظ الصورة محليًا كملف منفصل عن بيانات المنتج. يحمل سجل المنتج مرجع الصورة فقط.
- النسخة الاحتياطية المحلية تشمل بيانات النظام والصور في حزمة واحدة مشفرة بكلمة مرور المدير، قابلة للاستيراد على جهاز آخر؛ كلمة المرور الخاطئة أو الملف المعدل لا يكتب أي بيانات. التفاصيل: `docs/decisions/ADR-003-encrypted-local-backups.md`.
- النسخة الاحتياطية المحلية تضم الصور. إن لم تكن الصورة موجودة محليًا على جهاز، تظهر صورة افتراضية إلى أن تُستورد نسخة محلية تحتويها.
- يدعم البحث وإضافة المنتج بالباركود من قارئ USB على Windows، ومن كاميرا الهاتف على Android **كمسار أساسي معتمد** يعمل محليًا بعد أول تحميل للجهاز (لا قراءة سحابية أثناء البيع). تُختبر دقة القراءة والإضاءة على أصناف المحل الحقيقية.
- يُتتبع IMEI/Serial على مستوى القطعة عند الحاجة؛ ويُحظر تكرار المعرّف لنفس الصنف/المحل.

## المصادر والأثر التاريخي

- النظام القديم مؤرشف للعلم والتدقيق فقط: تبقى الشيفرة والاختبارات وملفات البناء والآثار التاريخية دون حذف أو تعديل. **لا يُشتق منه منطق جديد ولا تُنقل منه قاعدة عمل.**
- وثائق المشروع القديم وADRs في `archive/legacy-project/` مادة أرشيفية لا تحكم التصميم الجديد.
- ندرس سير العمل في أنظمة مثل Odoo وOpen Source POS وERPNext؛ لا نركب أنظمة كاملة معًا ولا ننسخ شيفرات قبل مراجعة الترخيص على مستوى الملفات والاعتماديات.
- ندرس سير العمل في أنظمة مثل Odoo وOpen Source POS وERPNext كمرجع أفكار فقط؛ لا نركب أنظمة كاملة معًا ولا ننسخ شيفرات قبل مراجعة الترخيص على مستوى الملفات والاعتماديات.

## معايير النجاح

1. يفتح البرنامج كتطبيق مثبت مستقل على Windows وAndroid.
2. يعمل Windows دون الإنترنت في الوظائف الأساسية، بما فيها البيع.
3. لا يستطيع مستخدم المبيعات الوصول المعتاد لبيانات الجملة أو تنفيذ صلاحيات الإدارة، وتُختبر صلاحيات كل عملية في طبقة التطبيق/البيانات وليس بإخفاء عناصر الواجهة فقط.
4. يُبحث عن المنتج بالباركود، ويُدعم التتبع الاختياري لـIMEI/Serial والصورة الرئيسية.
5. لا تضيع المعاملات المؤجلة، ولا تتكرر عند إعادة المحاولة، ويظهر تعارض المخزون بوضوح داخل الجهاز.
6. تُستورد نسخة محلية البيانات والصورة إلى جهاز آخر مع تحقق من سلامة الحزمة والروابط.
7. تمر اختبارات الأدوار، المخزون، المعاملات دون اتصال، النسخ والاستعادة، وترقيات قاعدة البيانات.

## الحدود والقيود

- النظام القديم مادة أرشيفية: لا يُعدَّل ولا يُستبدل ولا يُحذف. لا شرط لمساره في هذه المواصفة.
- لا توجد خدمة سحابية في V1. أي خدمة مستقبلية تتطلب قرارًا منفصلًا وفحص المصادقة وسياسات البيانات.
- لا تُخزن الصور داخل قاعدة البيانات أو كحقول كبيرة في سجل المنتج؛ الصورة ملف مستقل يُشار إليه بمرجع.
- لا تُحذف المنتجات المرتبطة بتاريخ مبيعات؛ تُؤرشف.
- لا يوجد خادم في V1، فلا تُرسل الصور خارج الجهاز.
- كل جهاز يعمل على قاعدة بياناته المحلية. لا تُعتمد سياسة بيع عبر أجهزة في V1.

## أوامر التحقق

لا يوجد بعد test runner أو build script للنظام الجديد؛ تُحدد الأوامر ضمن تجربة Tauri وتوثَّق في README الجديد قبل أول شريحة إنتاجية. أوامر المشروع القديم ليست أوامر بناء للنظام الجديد ولا تُستخدم كاختبارات له.

## نقاط تحتاج اعتمادًا قبل تثبيت التصميم

1. نطاق لاحق للمشتريات: أوامر الشراء والمستحقات والمدفوعات غير مدرجة في الإصدار الأول؛ التوريد المبسط (المورد + الكمية + تكلفة الوحدة) معتمد.
2. تفاصيل الاستعادة والاسترجاع: مُشغِّل لقطات النسخ الاحتياطي، سياسة الاحتفاظ، التحقق قبل الاستعادة، وفحوص السلامة — كلها **مفتوحة**؛ الاتجاه المعتمد في ADR-008 هو SQLite مع لقطات تلقائية.
3. تحديد طرق الدفع الفعلية، ونوع طابعة الإيصالات وطابعة الملصقات إن وُجدت؛ قارئ USB على Windows وكاميرا Android للباركود معتمدان.
4. ~~اختيار backend والاستضافة~~ — **لا ينطبق على V1**: لا خادم مركزي ولا قاعدة بيانات سحابية. يُنظر في المزامنة ضمن مرحلة معمارية منفصلة.
5. اختيار خوارزميات KDF/التشفير ومكتبتها للنسخ بعد مراجعة الأمن والتراخيص؛ قرار وجوب تشفير النسخ وكلمة مرور المدير معتمد في ADR-003. قاعدة البيانات المحلية غير مشفرة في الإصدار الأول.
6. تحديد مدد/شروط الضمان الافتراضية حسب نوع المنتج.
7. اعتماد نطاق ملصقات الباركود وأجهزة طباعة الملصق/الإيصال.
8. **تعريفات مؤشرات التقارير المالية** — قرار منتج مستقل: ما معنى `Total Sales` وما معنى `Net Profit`، وأي الحركات تدخل في كل منهما. لا يُشتق من أي تقرير سابق.
9. اعتماد قاعدة تقريب العملة الصغرى، ومحاسبة مرتجع البضاعة التالفة أو غير القابلة لإعادة البيع. **العملة محسومة** (`EGP` / القرش / خانتان عشريتان) ولا يُغلّق هذا البند؛ يلزم حسمه قبل شريحة المخزون أو البيع، أي قبل أول عملية قسمة في النظام. المرجع: القرار في `ADR-010`. — **ملاحظة 2026-10-07:** حُسمت قاعدة التقريب بموجب مواصفة التسليم §10 وسُجّل في `docs/decisions/ADR-013-costing-moving-average-and-fifo.md`؛ والتنفيذ يأتي مع محرك التكاليف.
