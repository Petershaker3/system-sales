# محل الموبايلات — مواصفات النظام المقترح

**الحالة:** مسودة للمراجعة قبل التنفيذ  
**التاريخ:** 2026-09-28

## الهدف

تطوير نظام إنتاجي لإدارة محل موبايلات، يستفيد من منطق المشروع الحالي ومن المصادر المفتوحة المناسبة، ويعمل كتطبيق مثبت على Windows وAndroid. يستمر جهاز Windows في البيع وإدارة التشغيل عند انقطاع الإنترنت، بينما يستخدم Android النظام عند الاتصال. تكون الواجهة عربية وRTL، مع صلاحيات واضحة، وبيانات منتجات قابلة للبحث بالباركود وتتبع اختياري للسيريال/IMEI.

## المستخدمون والأدوار

- **المستخدم الأساسي/المدير:** إدارة المنتجات والمخزون، مشاهدة أسعار الجملة والتكلفة والربح، وإدارة المستخدمين والتقارير والإعدادات وملفات العملاء.
- **مستخدم المبيعات:** تسجيل المبيعات والعمليات المسموحة له دون الاطلاع على أسعار الجملة أو إدارة المنتجات؛ يجوز له إدخال بيانات عميل جديدة للفاتورة دون تصفح سجل مشتريات العملاء.
- تُسجل العمليات والتعديلات والإلغاءات بمعرّف المستخدم المنفذ.
- إيقاف المنتج أو أرشفته يحافظ على ارتباطه بالفواتير وحركات المخزون السابقة؛ لا يُحذف سجل تاريخي نهائيًا من تدفق الاستخدام العادي.

## خريطة القدرات وحدود الوحدات

| المعرّف | المسؤولية | يعتمد على |
|---|---|---|
| `platform-data` | تطبيق Windows/Android، قاعدة البيانات المحلية، الإصدارات والترحيلات | — |
| `identity-access` | الحسابات والأدوار والصلاحيات وسجل التدقيق | `platform-data` |
| `catalog-media` | المنتجات والتصنيفات والباركود وطباعته وIMEI/Serial والصورة المحلية | `platform-data`, `identity-access` |
| `inventory-procurement` | سجل المخزون والجرد واستلام توريد مبسط باسم المورد والكمية وتكلفة الوحدة؛ لا أوامر شراء أو مستحقات موردين في الإصدار الأول | `catalog-media`, `identity-access` |
| `customer-records` | ملف عميل بسيط وربطه بالفاتورة/الصيانة/IMEI والضمان؛ الأجل والتقسيط خارج النطاق | `platform-data`, `identity-access` |
| `pos-sales` | البيع والمدفوعات والمرتجعات والإلغاء | `catalog-media`, `inventory-procurement`, `identity-access`, `customer-records` |
| `cash-reconciliation` | حركات الكاش وفتح/إغلاق الوردية ومطابقة العهدة | `pos-sales`, `identity-access` |
| `shop-operations` | الصيانة والمصروفات وغيرها من قدرات المشروع الحالي | `platform-data`, `identity-access`, `inventory-procurement`, `customer-records` |
| `sync-backup` | مزامنة البيانات المنظمة ونسخ البيانات والصور محليًا | كل وحدات البيانات |
| `reports` | مؤشرات وتقارير مبنية على المعاملات، مع فصل تعريفات التقارير القديمة عن الجديدة | `pos-sales`, `inventory-procurement`, `cash-reconciliation`, `shop-operations` |

**ترتيب البناء المقترح:** `platform-data` → `identity-access` → `catalog-media` و`customer-records` → `inventory-procurement` → `pos-sales` → `cash-reconciliation` و`shop-operations` → `sync-backup` و`reports`. تُبنى واجهات المزامنة والنسخ الاحتياطي في الأساس مبكرًا، ثم تُربط بالكيانات عبر شرائح كاملة.

## شكل التطبيق والتقنيات المرشحة

- تطبيق مثبت مستقل على Windows وAndroid، وليس تشغيلًا يطلب من المستخدم فتح المتصفح.
- `Tauri 2` هو المرشح الأول؛ يستخدم WebView داخليًا في نافذة التطبيق. المستودع الرسمي يذكر دعم Windows وAndroid: <https://github.com/tauri-apps/tauri>.
- **لا تُكشف واجهة SQL عامة للـWebView.** إضافة Tauri SQL توفر `execute/select` مباشرة للواجهة، ولا تعرض أمرًا لمعاملة متعددة الاستعلامات؛ لذلك لا تُعتمد كواجهة بيانات إنتاجية. مرجع المصدر: <https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/sql/src/commands.rs> و<https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/sql/src/wrapper.rs>.
- المرشح لبيانات التطبيق: `SQLx` داخل طبقة Rust مع أوامر Tauri محددة تتحقق من الدور وتنفذ الاستعلامات. توثق `SQLx Pool::begin` بدء معاملة و`Transaction` commit/rollback: <https://docs.rs/sqlx/latest/sqlx/struct.Pool.html#method.begin> و<https://docs.rs/sqlx/latest/sqlx/struct.Transaction.html>.
- الواجهة تكون مشتركة قدر الإمكان، لكن اختيار إطار الواجهة والـtoolchain النهائيين يتوقفان على تجربة تقنية قصيرة. تثبت إصدارات Tauri 2 وRust/SQLx المتوافقة بعد التجربة؛ لا تُستخدم إصدارات major alpha.
- لا يُختار backend الإنتاجي أو تُفعّل ملفات Supabase الحالية قبل فحص المصادقة وRLS والمزامنة على بيئة اختبارية. تقرير التدقيق القديم يصف تلك الملفات بأنها مرجعية وغير مختبرة.

### حد الثقة والصلاحيات

- الواجهة لا تحمل بيانات اعتماد قاعدة البيانات ولا تستدعي SQL خامًا. كل قراءة/كتابة تمر عبر أمر Rust مسمى ومتحقق من هوية الجلسة ودورها.
- أمر البيع يلتقط تكلفة البيع كسجل تاريخي، ويتحقق من الرصيد والسيريال، ثم يحفظ الفاتورة والأسطر وحركة المخزون داخل معاملة SQLx واحدة؛ فشل أي خطوة يلغي العملية كلها.
- سعر الجملة لا يرجع في نتائج أوامر دور المبيعات. حماية ملف قاعدة البيانات من مستخدم يملك صلاحيات نظام التشغيل نفسه حدّ ثقة منفصل؛ يُحدد في نموذج التهديد، ولا يُوعد بمنع مسؤول الجهاز من فحص البيانات دون تشفير/فصل حسابات مناسب.
- **مستوى الحماية المعتمد:** منع ظهور سعر الجملة واستخدامه عبر التطبيق لمستخدم المبيعات؛ لا يُشترط تشفير ملف قاعدة البيانات ضد من يملك وصولًا مباشرًا لملفات Windows أو صلاحيات مسؤول. لا يُدّعى أن صلاحيات التطبيق تمنع قراءة ملف SQLite مباشرة؛ تشفير النسخة الاحتياطية قرار منفصل.
- المال يُخزن بوحدات صحيحة من أصغر فئة للعملة (`amount_minor`)، لا `REAL`/`f64`. تعبر مبالغ Rust↔WebView كسلاسل أعداد صحيحة أو نوع يضمن عدم فقد الدقة؛ تُحوّل الواجهة للقيمة المعروضة ويُختبر round-trip.

## هيكل المشروع المقترح

يُثبت الهيكل النهائي بعد تجربة Tauri، لكن الحدود المقصودة هي:

```text
src-tauri/                  غلاف المنصات، أوامر محلية محدودة، صلاحيات النظام
src/app/                    بدء التطبيق والتنقل والحالة العامة
src/domain/                 قواعد العمل وأنواع المجال والتحقق
src/data/                   SQLite، المستودعات، الترحيلات، مزود المزامنة
src/modules/                identity, catalog, inventory, sales, operations, reports
src/shared/                 مكونات الواجهة والأدوات المشتركة
tests/unit/                 اختبارات منطق النطاق
tests/integration/          SQLite، المزامنة، النسخ والترحيل
tests/device/               سيناريوهات Windows وAndroid والأجهزة الطرفية
docs/superpowers/           المواصفات والخطط وقرارات التصميم الجديدة
archive/legacy-project/     وثائق النظام السابق المؤرشفة
```

هذا تقسيم مسؤوليات مبدئي؛ يُعدّل فقط عند ظهور قيد مثبت في تجربة المنصة، وتُسجل أسباب القرار في وثائق المشروع الجديد.

## أسلوب الكود المقترح

- أسماء الأنواع والواجهات والحقول البرمجية بالإنجليزية؛ نصوص المستخدم في ملفات رسائل عربية وRTL بدل بعثرتها في منطق المجال.
- منطق المجال مستقل عن مكونات الواجهة وقاعدة SQLite؛ الوصول للبيانات عبر مستودعات/خدمات واضحة.
- تُفعّل صرامة TypeScript إذا اختير TypeScript في تجربة الواجهة؛ يُحسم إطار الواجهة قبل scaffold التطبيق.
- معاملات البيع والمخزون تُنفذ كوحدة ذرية؛ لا تُحسب الأرصدة من واجهة أو من قيم قابلة للتعديل يدويًا دون سجل حركة.
- تجنب الحالة العامة القابلة للتغيير ونقل نمط global state من المشروع القديم دون مبرر واختبارات.

## استراتيجية الاختبار

- **وحدات:** صلاحيات الأدوار، حساب الإجمالي/التكلفة، قواعد الباركود والسيريال، ودورة حالات الفاتورة.
- **تكامل:** قيود SQLite ومعاملاتها وترحيلاتها؛ دفتر المخزون؛ outbox/cursor/idempotency؛ تصدير واستيراد النسخة والصور.
- **ترحيل بيانات:** fixtures اصطناعية من مخطط localStorage والنسخ القديمة، مع مطابقة عدد السجلات والأرصدة قبل وبعد.
- **أجهزة:** تثبيت وتشغيل Windows وAndroid، انقطاع الشبكة، الكاميرا، قارئ الباركود، والطابعة المستهدفة.
- **ذرية مالية:** فشل متعمد بعد حفظ سطر الفاتورة وقبل حركة المخزون يجب أن يترك قاعدة البيانات دون فاتورة/خصم جزئي؛ اختبار حقيقي على SQLite/SQLx وليس mock.
- **دقة نقدية:** اختبارات حدود تتحقق من تخزين المال كعدد صحيح ومن عدم تمريره عبر `REAL`/`f64` في قاعدة البيانات.
- **قبول:** مسارات manager/sales، بيع Windows offline ثم sync، ومنع أو إظهار تعارض البيع عبر الجهازين وفق السياسة المعتمدة.
- لا يوجد test runner أو build script للتطبيق الجديد بعد؛ تحدد الأوامر الدقيقة ضمن تجربة Tauri، وتُوثق في README الجديد قبل أول شريحة إنتاجية.

## حدود العمل

- **دائمًا:** الحفاظ على نسخة المصدر القديمة؛ الاختبار على نسخ بيانات؛ ترحيلات versioned؛ تدقيق كل عملية حساسة؛ عدم إسقاط معاملات مالية بصمت.
- **تتطلب موافقة:** backend والاستضافة؛ تغيير نطاق المشتريات؛ سياسة تسليم POS؛ تشفير قاعدة البيانات المحلية؛ أي تغيير في الأدوار أو إظهار التكلفة.
- **ممنوع:** استبدال بيانات المستخدم الأصلية مباشرة؛ حذف تاريخ منتج مرتبط بعمليات؛ إرسال صور المنتج ضمن sync الاعتيادي؛ تضمين أسرار خدمة في تطبيق العميل؛ اعتماد LWW يمحو فاتورة أو حركة مخزون بلا مراجعة.
- لا يُعتمد على واجهة JavaScript أو إضافة SQL ذات وصول خام كحد للصلاحيات؛ طبقة Rust هي نقطة الوصول الوحيدة لبيانات التطبيق.

## التشغيل دون اتصال والمزامنة

- يجب أن يواصل Windows تسجيل المبيعات والعمل الأساسي دون اتصال بالإنترنت.
- Android مثبت ويقدم وظائف النظام عند الاتصال؛ بيع Android يتطلب اتصالًا ومخزونًا حديثًا.
- تتزامن البيانات المنظمة بين النظامين، ولا تُرفع صور المنتجات تلقائيًا.
- لا تُقبل سياسة مزامنة تمحو معاملة بيع أو تتجاوز تعارض مخزون بصمت.
- **قرار معتمد في ADR-001:** نقطة بيع واحدة تملك حق تنفيذ عمليات البيع التي تغيّر المخزون. Windows يحتفظ بالملكية وهو قادر على البيع offline؛ Android لا ينفذ checkout أو تعديلًا يؤثر على رصيد البيع ما دام Windows مالكًا أو لديه عمليات غير متزامنة. التفاصيل: `docs/decisions/ADR-001-single-pos-ownership.md`.
- نقل ملكية البيع إلى Android يتطلب اتصال الجهازين، مزامنة طابور Windows بالكامل، ثم تحرير Windows للصلاحية واستلام Android لها. لا تنتهي الملكية آليًا عند غياب heartbeat؛ هذا يمنع takeover خاطئ أثناء استمرار Windows في العمل offline.
- عند فقد جهاز Windows نهائيًا مع احتمال وجود عمليات محلية غير متزامنة، يمنع البيع على Android حتى تسوية الحالة. إجراء الاستعادة القسرية/الجرد في هذه الحالة ما زال يحتاج قرارًا تشغيليًا، ولا يُنفذ بصمت.

## نموذج البيانات واستمرارية التاريخ

- سطر الفاتورة يحفظ لقطة وصف المنتج/الباركود والسعر والتكلفة والربح وقت العملية؛ تعديل سعر الشراء في كتالوج المنتج لا يعيد كتابة ربح عملية قديمة.
- **قرار معتمد في ADR-002:** متوسط تكلفة مرجح متحرك للأصناف الكمية، وتكلفة شراء فعلية لكل وحدة IMEI/Serial. تحفظ كل فاتورة بيع التكلفة المختارة كسnapshot؛ بيانات legacy تحافظ على snapshots ربحها المسجلة كما هي. التفاصيل: `docs/decisions/ADR-002-inventory-costing.md`.
- كتالوج الهاتف الحالي يحتوي كمية وسعر شراء وسجل شراء، أما كتالوج الإكسسوارات `mshop_ca` وكتالوج المستعمل `mshop_cu` فلا يحملان كمية مخزون. معاملات الإكسسوارات/المستعمل تحفظ اسمًا حرًا ولا ترتبط بمعرّف منتج ثابت. لا يمكن استنتاج أرصدة إكسسوارات أو أجهزة مستعملة من هذه البيانات؛ يلزم جرد افتتاحي يدخله المستخدم، ولا تُخترع كميات أثناء الترحيل.
- لا يوجد في المشروع القديم حقل باركود موحد؛ `internalCode` ليس باركودًا مؤكدًا. إنشاء الباركود وملصقاته وظيفة جديدة. يحتفظ محول البيانات بأوصاف المعاملات القديمة كلقطات تاريخية، ولا يربط أسماء متشابهة بمنتجات جديدة تلقائيًا.
- لا توجد حسابات موظفين قديمة ولا `createdBy` موثوق لكل سجل؛ سجلات الاستيراد القديمة تأخذ علامة `legacy-import` أو `createdBy=null`، ولا تُنسب بأثر رجعي إلى المدير أو البائع.
- مبيعات وصيانة النظام القديم قد تحمل `clientName` نصًا حرًا فقط؛ لا تُنشأ ملفات عملاء آلية بدمج الأسماء المتشابهة. يراجع المدير السجلات التي يمكن ربطها يدويًا، وإلا تبقى كـsnapshots نصية.
- **نطاق عميل معتمد:** اسم ورقم تواصل واحد اختياريان، وربط اختياري بالفاتورة/الصيانة/IMEI وسجل فترة الضمان. تسجل بداية ونهاية الضمان للجهاز/البيع؛ لا نظام مطالبات في الإصدار الأول. لا عنوان أو رقم قومي دون حاجة معلنة؛ المدير يشاهد التاريخ، ومستخدم المبيعات لا يتصفح سجل الشراء.

### تعريف التقارير المالية القديمة

قبل استبدال التقرير، تُحفظ القاعدة الحالية كتعريف تقرير مسمى ومتوافق للتاريخ القديم أو يوافق المالك صراحةً على تعريف جديد:

- إجمالي المبيعات القديم = `accessory sell + software price + cash amount` فقط؛ لا تدخل مبيعات الهواتف أو إجمالي فواتير الإصلاح في هذا الرقم.
- صافي الربح القديم = أرباح الإكسسوارات والمستعمل + قيمة الكاش + قيمة السوفت وير + أرباح الهواتف + أرباح الإصلاح غير الملغى − المصروفات.
- تُستبعد المعاملات ذات `_rolled` وإصلاحات `cancelled` من الحسابات المحددة في `computeFinancialTotals`.
- في الكود القديم، `cT` يجمع `amount` لكل حركات الكاش بما فيها «سحب»، فيدخل السحب ضمن إجمالي المبيعات؛ سلوك تاريخي وُثّق ولم يُصحَّح.
- تُعرض الأرقام الجديدة والقديمة بأسماء واضحة؛ لا تتغير دلالة «إجمالي المبيعات» بصمت.
- **إثبات الاستيراد:** قارئ تصدير legacy يكشف الشكل لكل سجل على حدة لأن القسم الواحد قد يخلط الشكلين (`dev_extracted/dev/js/storage.js:110-138`). المحوّل لا ينشئ `productId` من اسم حر ولا يستنتج أرصدة إكسسوارات/مستعمل، ويضع `origin=legacy-import` و`createdBy=null` لكل سطر بلا مستخدم موثوق. شاهد: `spikes/legacy-import/`.

## المنتجات والصور والباركود

- لكل منتج صورة رئيسية واحدة؛ يختارها المستخدم من ملف أو يصورها بكاميرا Android.
- تحفظ الصورة محليًا كملف منفصل عن بيانات المنتج. يحمل سجل المنتج مرجع الصورة فقط.
- النسخة الاحتياطية المحلية تشمل بيانات النظام والصور في حزمة واحدة مشفرة بكلمة مرور المدير، قابلة للاستيراد على جهاز آخر؛ كلمة المرور الخاطئة أو الملف المعدل لا يكتب أي بيانات. التفاصيل: `docs/decisions/ADR-003-encrypted-local-backups.md`.
- المزامنة الاعتيادية لا ترفع الصور. إن لم تكن الصورة موجودة محليًا على جهاز، تظهر صورة افتراضية إلى أن تُستورد نسخة محلية تحتويها.
- يدعم البحث وإضافة المنتج بالباركود من قارئ USB على Windows، ومن كاميرا الهاتف على Android **كمسار أساسي معتمد** يعمل محليًا بعد أول تحميل للجهاز (لا قراءة سحابية أثناء البيع). تُختبر دقة القراءة والإضاءة على أصناف المحل الحقيقية.
- يُتتبع IMEI/Serial على مستوى القطعة عند الحاجة؛ ويُحظر تكرار المعرّف لنفس الصنف/المحل.

## الاستفادة من المشروع والمصادر المفتوحة

- مصدر المشروع الحالي الذي تمت مراجعته هو `dev_extracted/dev/`. تبقى الشيفرة والاختبارات وملفات البناء والآثار التاريخية دون حذف، ويُعاد استخدام المنطق الذي يثبت صلاحيته بعد فحصه واختباره.
- تعليمات وتقارير المشروع القديم وADRs نُقلت إلى `archive/legacy-project/` ولا تحكم التصميم الجديد.
- ندرس سير العمل في أنظمة مثل Odoo وOpen Source POS وERPNext؛ لا نركب أنظمة كاملة معًا ولا ننسخ شيفرات قبل مراجعة الترخيص على مستوى الملفات والاعتماديات.
- يظل استيراد بيانات التطبيق القديم والنسخ الاحتياطية جزءًا من خطة الترحيل، ولا تُجرى تجربة على النسخة الوحيدة من بيانات المستخدم.

## معايير النجاح

1. يفتح البرنامج كتطبيق مثبت مستقل على Windows وAndroid.
2. يعمل Windows دون الإنترنت في الوظائف الأساسية، بما فيها البيع.
3. لا يستطيع مستخدم المبيعات الوصول المعتاد لبيانات الجملة أو تنفيذ صلاحيات الإدارة، وتُختبر صلاحيات كل عملية في طبقة التطبيق/البيانات وليس بإخفاء عناصر الواجهة فقط.
4. يُبحث عن المنتج بالباركود، ويُدعم التتبع الاختياري لـIMEI/Serial والصورة الرئيسية.
5. لا تضيع معاملات Windows المؤجلة، ولا تتكرر عند إعادة المحاولة، وتُعرض تعارضات المخزون بوضوح.
6. تستورد نسخة محلية البيانات والصورة إلى جهاز آخر مع تحقق من سلامة الحزمة والروابط.
7. ينجح ترحيل نسخة اختبار من بيانات المشروع القديم مع تطابق عدادات المعاملات والمخزون والتقارير قبل/بعد.
8. تمر اختبارات الأدوار، المخزون، المعاملات غير المتصلة، المزامنة، النسخ والاستعادة، وترقيات قاعدة البيانات.

## الحدود والقيود

- لا يُغيّر المشروع القديم أو يُستبدل قبل إنشاء نسخة قابلة للاسترجاع وإثبات مسار الترحيل.
- لا تُفعل مزامنة Supabase أو أي خدمة حية قبل قرار backend وفحص المصادقة وسياسات البيانات والنسخ.
- لا تُخزن الصور كـBase64 داخل localStorage أو كحقول ضخمة في سجل المنتج.
- لا تُحذف المنتجات المرتبطة بتاريخ مبيعات؛ تُؤرشف.
- لا تُرسل الصور إلى الخادم ضمن المزامنة الاعتيادية.
- لا يُعتمد البيع من جهازين على أرصدة قديمة دون سياسة حجز/تعارض معتمدة.

## أوامر التحقق المعروفة للمشروع القديم

تُستخدم هذه الأوامر لتسجيل baseline قبل الترحيل فقط، وليست أوامر بناء التطبيق الجديد:

- `node dev_extracted/dev/tests/rc_closure_test.js`
- `node dev_extracted/dev/tests/phone_date_roundtrip_test.js`
- `node dev_extracted/dev/tests/gas_config_boundary_test.js`
- بناء النسخة القديمة: `python build.py` من `dev_extracted/dev/`؛ سجل التسليم يذكر خطأ طباعة Windows بعد كتابة المخرج، لذا يجب فحص exit code ومحتوى الملف.

## نقاط تحتاج اعتمادًا قبل تثبيت التصميم

1. نطاق لاحق للمشتريات: أوامر الشراء والمستحقات والمدفوعات غير مدرجة في الإصدار الأول؛ التوريد المبسط (المورد + الكمية + تكلفة الوحدة) معتمد.
2. اعتماد إجراء الاسترداد الإداري عند فقد Windows وفيه معاملات offline غير متزامنة؛ سياسة الملكية العادية معتمدة في ADR-001.
3. تحديد طرق الدفع الفعلية، ونوع طابعة الإيصالات وطابعة الملصقات إن وُجدت؛ قارئ USB على Windows وكاميرا Android للباركود معتمدان.
4. اختيار backend والاستضافة وتكلفتها وسياسة الاحتفاظ بالنسخ.
5. اختيار خوارزميات KDF/التشفير ومكتبتها للنسخ بعد مراجعة الأمن والتراخيص؛ قرار وجوب تشفير النسخ وكلمة مرور المدير معتمد في ADR-003. قاعدة البيانات المحلية غير مشفرة في الإصدار الأول.
6. تحديد مدد/شروط الضمان الافتراضية حسب نوع المنتج.
7. اعتماد نطاق ملصقات الباركود وأجهزة طباعة الملصق/الإيصال.
8. اعتماد جرد افتتاحي للإكسسوارات والأجهزة المستعملة؛ بيانات النظام القديم لا تحمل أرصدتها.
9. اعتماد الحفاظ على تعريفات التقارير القديمة أو تغييرها، خصوصًا استثناء مبيعات الهواتف/الإصلاح من إجمالي المبيعات.
10. اعتماد قاعدة تقريب العملة الصغرى ومحاسبة مرتجع البضاعة التالفة أو غير القابلة لإعادة البيع.
