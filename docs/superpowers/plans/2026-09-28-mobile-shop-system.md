# نظام محل الموبايلات — خطة التنفيذ

> **لمنفذي الوكلاء:** تُنفذ كل شريحة بعد مراجعة مواصفات النظام في `docs/superpowers/specs/2026-09-28-mobile-shop-system.md` وموافقة المالك على قرارات المرحلة. لا تُستخدم الوكلاء الفرعيون دون طلب صريح.

**الهدف:** تحويل وظائف محل الموبايلات الحالية إلى تطبيق مثبت وموثوق على Windows وAndroid، مع بيع offline على Windows، صلاحيات مستخدمين، مخزون وباركود، مزامنة منظمة، ونسخ محلية تشمل الصور.

**المعمارية المقترحة:** تطبيق Tauri متعدد المنصات بواجهة مشتركة، وSQLite تُدار حصرًا من Rust عبر أوامر محدودة، لا من `WebView` باستعلامات SQL حرة. تستخدم أوامر Rust صلاحيات الدور ومعاملات SQLx الفعلية؛ المال أعداد صحيحة بوحدة العملة الصغرى. يبقى Windows نقطة البيع offline؛ Android يستخدم البيانات online ولا يرفع الصور. لا يُعتمد backend حتى تمر مراجعة المصادقة والتعارض.

**التقنيات المرشحة:** Tauri 2 مثبت على major version 2، SQLx/SQLite داخل Rust، TypeScript للواجهة المشتركة، وخدمة مزامنة يختارها المالك بعد تقييم التكلفة وRLS. إضافة Tauri SQL مفيدة في التجربة فقط؛ لا تُعتمد للبيانات الإنتاجية لأنها تكشف `execute/select` للواجهة ولا توفر أمر معاملة مركبة. إطار الواجهة وbackend ليسا قرارين نهائيين حتى اجتياز مرحلة الإثبات التقني.

**المواصفات:** `docs/superpowers/specs/2026-09-28-mobile-shop-system.md`

## قيود عامة

- الاستهداف الأول: Windows وAndroid فقط؛ نافذة تطبيق مستقلة، لا تشغيل يتطلب فتح المتصفح.
- فرع واحد مبدئيًا؛ لا يُبنى نظام فروع كامل إلا بقرار لاحق.
- البيع دون إنترنت على Windows إلزامي؛ البيع على Android يحتاج اتصالًا ومزامنة مقبولة.
- تُراجع سياسة نقطة البيع الواحدة قبل السماح بتعديلات مخزون متزامنة بين جهازين.
- صورة رئيسية واحدة لكل منتج؛ الصور لا تتزامن تلقائيًا، لكنها تدخل ضمن النسخة المحلية القابلة للاستيراد.
- `IMEI/Serial` اختياري للقطعة؛ الباركود مدخل أساسي للبحث والبيع.
- الدور الأساسي يرى أسعار الجملة والتكلفة ويدير المنتجات؛ موظف المبيعات يسجل العمليات المسموحة فقط.
- كل بيانات المشروع القديم تظل محفوظة؛ لا تُحوّل البيانات الحية أو تُستبدل قبل نجاح تجربة ترحيل واستعادة على نسخة اختبار.
- لا تُفعّل بيانات اعتماد أو مشروع Supabase حالي قبل التحقق من الملكية وRLS والمخطط.
- لا commits أو نشر إلا بطلب منفصل من المالك.

## خريطة القدرة وترتيب الاعتماد

```text
platform-data
  └── identity-access
        ├── catalog-media
        │     └── inventory-procurement
        │            └── pos-sales
        │                  └── cash-reconciliation
        ├── customer-records (اختياري، بقرار مالك)
        │     ├── pos-sales
        │     └── shop-operations (repairs)
        └── shop-operations (expenses)

inventory-procurement يتصل أيضًا بـshop-operations عند استهلاك قطع الصيانة. sync-backup يتصل بكل وحدات البيانات؛ reports يقرأ pos-sales وinventory-procurement وcash-reconciliation وshop-operations. المرجع الحاكم لعلاقات الاعتماد هو جدول المواصفات.
```

هذه الوثيقة هي خارطة المبادرة وترتيب الاعتماد. بعد اعتمادها ونتيجة تجربة المنصة، يُكتب spec وخطة تنفيذ قصيرة لكل وحدة مستقلة قبل تنفيذها؛ لا تُدمج الوحدات ذات البيانات والصلاحيات المختلفة في مهمة تنفيذ واحدة.

### المهمة 1.3: إثبات Tauri على الجهازين

**النطاق:** مشروع spike معزول، لا يغيّر ملفات التطبيق القديم.

**الحالة (2026-09-29):** نواة البيع مُثبتة على جهاز فعلي. ما أُثبت بالدليل:

- **Android** (SM-N976N · Android 12 · arm64-v8a): SQLite + ترحيلان متتاليان + rollback كامل بعد حقن فشل (قراءة `spike.db` الحقيقي على الجهاز: `invoices=1 · invoice_lines=1 · orphan_lines=0`)، المال `INTEGER`، الكتالوج بلا تكلفة.
- **Android Offline:** قراءة باركود ناجحة والكاميرا معطلة الشبكة (`airplane_mode_on=1` · `ping → Network is unreachable`).
- **Windows:** نافذة native تستضيف `msedgewebview2` (لا متصفح)، صفر sockets، صفر رابط خارجي.
- **قلب واحد:** دالة Rust واحدة تعطي نفس بصمة القبول على النظامين حرفيًا، فالمنطق مشترك وغير مكرر.

**قيد معماري مسجَّل في `ADR-004`:** النموذج المُضمَّن عبر `com.google.mlkit:barcode-scanning` كسر القراءة (اختبار A/B)، فالقرار يربط المسح بـGoogle Play Services، وأجهزة بلا GMS قيد توافق صريح.

**بند HID مفتوح:** الكود وآلة الحالة وبوابة التركيز مكتملة باختبارات آلية 10/10، لكن **القبول الفيزيائي لم يُنفَّذ** — لا يوجد قارئ باركود متصل، والاختبارات تستدعي `on_key()` مباشرة فلا تثبت وصول أحداث ويندوز الحقيقية إلى الخطّاف. المسار البديل عبر Bluetooth HID متاح تقنيًا لكنه معطَّل على هذا الكمبيوتر لعدم وجود راديو بلوتوث، ولم يُشترَ dongle لأن الهدف إثبات مسار USB نفسه. التفاصيل والقيود في `ADR-004`.

**التحقق العملي:**
- حزمة Windows تفتح نافذة تطبيق دون متصفح، وتعمل بعد قطع الشبكة.
- حزمة Android تُثبت وتفتح واجهة مشتركة.
- اتصال SQLite من طبقة Rust على النظامين، وترحيلتان متتاليتان دون فقد السجل.
- استدعاء frontend لأمر مسمى يعيد كتالوج البيع بلا تكاليف؛ لا يوجد API من WebView ينفذ `SELECT/UPDATE` عامًا.
- أمر Rust يحفظ فاتورة ويخصم المخزون بمعاملة `SQLx`؛ يُحقن فشل بين الخطوتين ويُثبت rollback كامل.
- المبلغ يُرسل/يُحفظ كوحدة صحيحة ولا يمر عبر `REAL` أو `f64`.
- اختيار صورة ملف وتصوير صورة بكاميرا Android يعملان؛ تحفظ صورة واحدة محليًا.
- قارئ الباركود HID يكتب قيمة قابلة للالتقاط في حقل البيع على Windows. **القبول الفيزيائي معلّق**: لا يوجد قارئ متصل حاليًا، ويجري إغلاق البند بقارئ USB حقيقي دون تغيير الكود. يُجرّب توليد ملصق وطباعة عينة على الطابعة المقصودة.
- مسح الباركود بالكاميرا على Android هو المسار الأساسي المعتمد، ويعمل **محليًا بالكامل** بعد أول تحميل: نموذج/مكتبة القراءة تُضمَّن في حزمة التطبيق ولا تُحمَّل من الشبكة أثناء القراءة. إن لم يكن التطبيق قد حُمِّل بعد على جهاز جديد، تُعرض رسالة «حمّل التطبيق مرة واحدة قبل المسح بالكاميرا» بدل التعطل. تُختبر جودة القراءة والإضاءة والسرعة على أصناف المحل الحقيقية.

**قرار الخروج:** اعتماد Tauri 2 بعد نجاح المعايير، أو إيقاف التنفيذ وكتابة مقارنة/قرار معماري جديد لبديل أصلي مثل .NET MAUI. لا يُستبدل الغلاف تلقائيًا مع إبقاء افتراضات SQLx/Rust/IPC كما هي.

### المهمة 1.4: إثبات استيراد بيانات legacy قبل تثبيت schema

**الحالة:** أُثبتت 2026-09-28 في `spikes/legacy-import/` (spike قابل للحذف). النتيجة: `node spikes/legacy-import/import_probe.mjs` → PASS (exit 0) على بيانات اصطناعية تغطي يومين والشكلين المختلطين.

**نتائج مثبتة تُغيّر التصميم:**
- **خلط الأشكال داخل نفس القسم:** ملف تصدير legacy قد يحتوي سجلات بشكل «قاعدة بيانات» (`snapshotName`, `sellAmount`, `walletName`, `snapshotCategory`, `snapshotModelName`) وسجلات بالشكل المحلي القديم في المصفوفة نفسها. أي محول يفترض شكلًا واحدًا لكل قسم يفقد بيانات. الكشف يتم لكل سجل على حدة. (`dev_extracted/dev/js/storage.js:110-138`)
- **`cT` تجمع السحب مع الإيداع:** في `computeFinancialTotals` يكون `cT` مجموع `amount` لكل حركات الكاش بلا إشارة للنوع، فيدخل السحب ضمن «إجمالي المبيعات». سلوك تاريخي وُثّق في الـspike ولم يُصحَّح؛ تسمية «إجمالي المبيعات» في النظام الجديد يجب ألا تكرّر هذا الالتباس.
- **الأقسام تختلف في معنى الوصف:** وصف الكاش = اسم المحفظة/الخدمة، ووصف المصروف = فئته، ووصف الصيانة = العلامة+الموديل. محوّل عام يفترض حقل اسم واحدًا يعلّم سجلات صحيحة كمراجعة.
- **لا رصيد للإكسسوارات/المستعمل ولا باركود ولا مستخدم في المصدر:** الجداول `mshop_ca`/`mshop_cu` بلا حقول كمية، ومعاملاتها بأسماء حرة بلا `productId`. الجرد الافتتاحي يبقى بوابة إلزامية.
- **الصيانة محلية دائمًا:** `repairs` غير مسجّلة في `ENTITY_MAPPERS_REGISTRY`، فلا شكل DB لها.

**المتبقي قبل الإنتاج:** استبدال الـfixture الاصطناعي بتصدير حقيقي من نسخة المتجر (بإذن المالك)، وتأكيد صيغة ملف التصدير (JSON عادي أم `.mshop` مشفر)، ومحوّل إنتاجي يوفي بنفس شروط القبول الستة.

**النطاق الأصلي للمرجع:** قراءة فقط على تمثيل اصطناعي للمفاتيح `mshop_inventory`, `mshop_ca`, `mshop_cu`, `mshop_d_YYYY-MM-DD`, `mshop_repair_parts`. لا يعتمد على تشغيل `restoreSecureBackup()` في التطبيق القديم.

**القبول:** يحفظ سجل المعاملة القديم كما هو، ويسجل `legacy-import` عند غياب المستخدم، ولا يربط أسماء المنتجات الحرة تلقائيًا، ولا ينشئ رصيد إكسسوارات غير موجود في المصدر. تحدد نتيجة التجربة حقول SQLx ونسخة backup قبل كتابة بقية الوحدات.

**التحقق:** مطابقة أعداد المعاملات لكل partition، الأصناف/الأرصدة الموجودة فعليًا فقط، لقطات الشراء/البيع/الربح، وقيم التقرير القديم. حالات غير قابلة للمطابقة تخرج كتقرير مراجعة لا كتخمين.

## المرحلة 2 — أساس التطبيق والبيانات

### المهمة 2.1: تثبيت هيكل التطبيق وعقود الوحدات

**المخرجات:** مستودع التطبيق الجديد/هيكل `src-tauri/` والواجهة، حدود واضحة لـdomain/data/UI، إعدادات بيئة الاختبار، وثيقة اختيار إطار الواجهة وترخيص كل اعتماد جديد.

**القبول:** أوامر التطوير والبناء والاختبار مثبتة في README جديد؛ ملفات المصدر القديمة تظل مستقلة وغير مستبدلة.

**التحقق:** بناء نظيف لتطبيقي Windows وAndroid على بيئتيهما؛ اختبار تشغيل شاشة بدء فارغة على كل منصة.

### المهمة 2.2: قاعدة SQLite والترحيلات

**الجداول الأولية:** `users`, `roles`, `categories`, `products`, `barcodes`, `serialized_units`, `stock_movements`, `sales`, `sale_lines`, `payments`, `cash_sessions`, `media_assets`, `audit_events`, `sync_outbox`, `sync_cursors`. يضاف جدول/رابط `customers` بعد اعتماد نطاق العملاء.

**القبول:** معرّفات ثابتة UUID، قيود فريدة مناسبة للباركود/السيريال، حقول تدقيق للمنشئ والمعدل، ومبالغ صحيحة بالوحدة الصغرى للعملة. الأصناف الكمية تتبع المتوسط المرجح والوحدات المتسلسلة تكلفة الوحدة حسب ADR-002. تحفظ سطور المعاملات snapshots للوصف والسعر والتكلفة والربح. لا يُجبر سجل legacy بلا مستخدم على `createdBy` مزيف. تستخدم migrations إصدارية SQLx محفوظة في ملفات مستقلة؛ قبل migration إنتاجي تؤخذ نسخة قابلة للاستعادة، وخطة rollback الأساسية استعادة النسخة ثم forward-fix، لا افتراض تشغيل `Down` تلقائي.

**التحقق:** اختبارات SQLite للقيود والمعاملات والترحيل من قاعدة فارغة ومن الإصدار السابق.

### المهمة 2.3: حسابات offline وهوية الدور

**القبول:** حساب مدير وحساب مبيعات يعملان دون اتصال على Windows؛ يحتفظ Rust بجلسة مرتبطة بهوية المستخدم ودوره المستخرج من قاعدة البيانات، ولا يثق بأسماء الأدوار أو صلاحيات يرسلها frontend. معرّف الجلسة opaque وعشوائي وينتهي عند الخروج/القفل، وتُطلب إعادة مصادقة عند كشف بيانات الجملة. يخزن verifier آمن لا PIN/كلمة مرور صريحة، ويُحدد حد محاولات القفل والتبديل قبل إصدار المستخدمين.

**التحقق:** اختبارات فتح جلسة، credential خاطئ، تبديل مستخدم، قفل، وانتهاء/إعادة مصادقة الإجراء الإداري؛ ينجح ذلك offline على Windows.

### المهمة 2.4: بوابة Rust لقاعدة البيانات والصلاحيات

**القبول:** جميع قراءات/كتابات التطبيق تمر عبر أوامر نطاق محددة تستخدم SQLx. أمثلة واجهات: `getSaleCatalog(sessionId)` يعيد سعر البيع دون الشراء؛ `getManagerProduct(sessionId, productId)` يعيد التكلفة بعد تحقق المدير؛ `createSale(sessionId, SaleInput)` يتحقق من الجلسة والدور والمخزون وينفذ المعاملة. ممنوع command من نوع `executeSql(sql)` أو `selectSql(sql)` للـWebView. هذا يمنع كشف السعر عبر الاستخدام الطبيعي للتطبيق؛ وصول مباشر لملف SQLite خارج التطبيق غير محمي بالتشفير في الإصدار الأول، ولا تدّعي الخطة منعه.

**التحقق:** اختبارات مباشرة لاستدعاء أمر محمي بجلسة مبيعات ورفضه، عدم ظهور حقل التكلفة في نتيجة كتالوج البيع، وفشل منتصف معاملة البيع دون أي كتابة جزئية. اختبر integer money round-trip فوق وتحت الحدود المعقولة.

## المرحلة 3 — شرائح المجال الأساسية

### المهمة 3.1: كتالوج موحد جديد والباركود والصورة

**القبول:** إنشاء/تعديل/أرشفة تصنيفات ومنتجات؛ كود باركود مستقل عن `internalCode` مع ربط/إدخال باركود، ومسار طباعة ملصق مقروء يختبر على الطابعة المتفق عليها؛ صورة رئيسية واحدة من ملف أو كاميرا Android تحفظ محليًا. تسجيل الباركود يتم من قارئ USB على Windows ومن كاميرا Android كمسار أساسي. لا تستنتج بيانات/رصيد من المعاملات الحرة القديمة.

**التحقق:** بحث بالباركود يعيد منتجًا واحدًا من المسارين (قارئ USB على Windows، كاميرا Android محليًا)؛ تكرار الباركود يُرفض؛ المنتج وصورته يستمران بعد إعادة التشغيل offline؛ دور المبيعات يحصل على السعر والصورة فقط، لا الشراء/الربح.

### المهمة 3.2: تتبع القطعة الفردية

**القبول:** نوع المنتج يحدد هل يتتبع بالكمية أم بقطعة IMEI/Serial؛ لكل قطعة حالة stock identity، ويمنع تكرار المعرّف أو البيع بعد عدم التوفر.

**التحقق:** اختبارات استلام/بيع/مرتجع/إلغاء، وIMEI مكرر بين online/offline يظهر تعارضًا يدوي الحل بدل إسقاط بيع.

### المهمة 3.3: سجل المخزون والجرد الافتتاحي

**القبول:** استلام توريد مبسط يسجل اسم المورد وأصناف التوريد والكمية وتكلفة الوحدة والمستخدم والتاريخ؛ لا يتضمن أمر شراء أو حساب مستحقات/مدفوعات للمورد. الاستلام والتسوية والبيع والمرتجع حركات مصدرها معروف. تتحدث تكلفة الأصناف الكمية بالمتوسط المرجح؛ تحفظ تكلفة كل وحدة IMEI/Serial. يُسجل الجرد الافتتاحي للإكسسوارات والأجهزة المستعملة كحركة جديدة مع موافقة المدير؛ لا تُختلق أرصدة من `mshop_ca`/`mshop_cu`.

**التحقق:** رصيد كل صنف يساوي الحركة الافتتاحية زائد كل الحركات؛ مطابقة مستقلة لدفتر الحركة بعد بيع/مرتجع/تسوية.

**قرار نطاق:** الموردون وأوامر/فواتير الشراء وتوزيعها على الأصناف ضمن الإصدار الأول يتوقف على اعتماد المهمة 1.1.

### المهمة 3.4: البيع دون إنترنت على Windows

**القبول:** المسح والبحث، سلة، سعر/خصم حسب الصلاحية، دفع وإيصال، تعليق/إلغاء/مرتجع؛ يحتفظ كل سطر بوصف وسعر وتكلفة لحظة البيع. أمر Rust يحفظ الفاتورة والأسطر والدفع وخصم المخزون بمعاملة SQLx واحدة، بمعرّف idempotency ثابت.

**التحقق:** بيع offline، فشل مصطنع بين كل خطوتين، إغلاق مفاجئ، إعادة تشغيل، ومحاولة رفع العملية مرتين؛ يجب ألا يظهر قيد جزئي أو فاتورة مكررة.

### المهمة 3.5: وردية الكاش ومطابقة العهدة

**القبول:** فتح وردية باسم المستخدم ورصيد افتتاحي اختياري، إسناد مدفوعات الكاش للوردية، تسجيل السحب/الإضافة بسبب، إغلاقها بعدّ النقد الفعلي، وإظهار فرق العهدة؛ لا تعد هذه العملية بديلًا لتعريف `total sales` التاريخي.

**التحقق:** وردية بها cash/card/مصروف/سحب؛ يطابق المتوقع مع الفعلي وتظهر فروقات موثقة باسم المستخدم.

### المهمة 3.6: المزامنة وبيع Android online

**القبول:** backend يطبق صلاحيات لكل مستخدم، سجل تغييرات/إصدارات ورفع idempotent. لا تتزامن الصور. بيع Android لا يقبل إلا إذا كان الجهاز يملك نقطة البيع وفق ADR-001، ولا يعمل أثناء امتلاك Windows لها أو وجود عمليات محلية غير متزامنة.

**التحقق:** عند Windows owner/offline يرفض Android checkout وتعديل المخزون؛ بعد sync كامل وrelease/acquire صريح ينجح Android checkout ويرفض Windows checkout حتى يستعيد الملكية. اختبر أن heartbeat المنقطع لا ينقل الملكية تلقائيًا، واختبر مسار recovery بعد جرد يدوي مع سجل تدقيق.

### المهمة 3.7: ملفات العملاء والربط بالضمان

**القبول:** اسم ورقم تواصل واحد اختياريان؛ يُربط العميل بالفاتورة أو الصيانة أو IMEI. يخزن البيع بداية ونهاية فترة الضمان المحددة للجهاز؛ لا مطالبات أو مراحل صيانة ضمان في الإصدار الأول. مستخدم المبيعات يستطيع إدخال عميل جديد للفاتورة ولا يتصفح سجل الشراء؛ المدير يملك البحث والتاريخ. لا يُجمع عنوان/رقم قومي ولا يضاف أجل/تقسيط.

**التحقق:** lookup للعميل والجهاز المسلسل، اختبار منع دور المبيعات من قراءة تاريخ العميل، وحساب/عرض تاريخ انتهاء الضمان من التواريخ المحفوظة، واختبارات روابط الفاتورة/الصيانة بعد الاستيراد.

## المرحلة 4 — قدرات المتجر والتحليلات

### المهمة 4.1: المصروفات والصيانة

**القبول:** ترحيل وظائف المشروع الحالي التي يعتمدها المالك فقط، مع صلاحيات وسجل تدقيق وروابط صحيحة للمخزون والبيع والعميل عند اعتماده. سحب مخزون قطع الصيانة يسجل حركة صريحة.

**التحقق:** اختبارات مالية ومراجعة يدوية لمجموعة حركات مرجعية قبل/بعد ترحيل المنطق.

### المهمة 4.2: قواعد التقارير والتحليلات

**القبول:** توثيق تعريف كل KPI. يحسب legacy-compatible report الصيغة الموثقة في المواصفات باستخدام snapshots التكلفة التاريخية؛ أي تغيير يُعتمد كـnew metric باسم جديد. تقارير الوردية مستقلة عن إجمالي المبيعات التاريخي، والمحتوى يتبع الدور.

**التحقق:** golden fixtures تشمل إكسسوارًا ومستعملًا وكاشًا وسوفت وير وهاتفًا وإصلاحًا ملغى ومصروفًا و`_rolled`؛ قارن كل metric بالصيغة المعتمدة.

## المرحلة 5 — الصور والنسخ والترحيل والإطلاق

### المهمة 5.1: حزمة نسخة احتياطية محلية

**القبول:** حزمة versioned مشفرة بكلمة مرور المدير تضم قاعدة البيانات والصورة الرئيسية لكل منتج وmanifest يربط الصور بمعرفاتها؛ الاستيراد يفكها ويتحقق من السلامة ثم يعرض أثر الاستعادة قبل الاستبدال. كلمة مرور خاطئة أو محتوى معدل/تالف يفشل مغلقًا ولا يغير قاعدة الجهاز. لا تُرفع الصور ضمن sync. اختيار خوارزمية/KDF ومكتبة التشفير موثق في ADR-003 ويتحقق قبل التنفيذ.

**التحقق:** إنشاء نسخة مشفرة، استيرادها على Android نظيف بكلمة المرور، مطابقة أعداد الكيانات والصور وhashes؛ اختبارات كلمة مرور خاطئة وملف معدل/تالف وسياسة overwrite والتأكد من عدم حدوث أي كتابة عند الفشل.

### المهمة 5.2: أداة استيراد legacy المثبتة بالمطابقة

**القبول:** قراءة نسخة export مؤكدة من مخطط legacy دون كتابة أو استعادة داخل التطبيق القديم. تحفظ معاملات الأسماء الحرة و`buy/sell/profit` كـsnapshots؛ السجلات بلا مستخدم تأخذ `legacy-import`; كتالوج الإكسسوارات لا ينتج أرصدة، وتحتاج الكميات جردًا افتتاحيًا جديدًا. لا يُصلح `restoreSecureBackup()` القديم كشرط للاستيراد؛ إذا كان المصدر `.mshop` مشفرًا، يُفك ويُقرأ بمسار استيراد مستقل مُختبر بعد تأكيد صيغة الملف. لا تُستخدم النسخة الوحيدة من بيانات المحل.

**التحقق:** fixtures لكل نوع/تاريخ، مطابقة أعداد المعاملات وقيم snapshots ونتائج التقارير legacy، وإظهار قائمة سجلات غير قابلة للربط للمراجعة. تأكيد عدم اختراع product links أو accessory quantities؛ إعادة الاستيراد idempotent أو ترفض التكرار بوضوح.

### المهمة 5.3: اختبارات قبول وأمان وأجهزة وإصدار

**القبول:** حزم Windows وAndroid موقعة/قابلة للتثبيت، ترقية نسخة قديمة آمنة، استعادة كاملة، وقائمة أجهزة مدعومة للماسح والطابعة والكاميرا.

**التحقق:** مسار مستخدم كامل لكل دور على كل منصة، Windows offline ثم sync، Android online، فحص dependencies/licenses، ونسخة احتياطية تُستعاد على جهاز/ملف جديد.

## مخاطر ووسائل المعالجة

| الخطر | الأثر | المعالجة قبل التوسع |
|---|---|---|
| Tauri أو SQLx SQLite Android أو الكاميرا/الطابعة لا تلائم الأجهزة | إعادة بناء مكلفة | spike على Windows وAndroid؛ لا استخدام لواجهة SQL plugin العامة في الإنتاج |
| وصول frontend إلى SQL خام | تجاوز صلاحيات المدير/كشف التكلفة | أوامر Rust مسماة فقط، لا `executeSql/selectSql`، واختبار استدعاء غير مصرح |
| اتصال SQL pool لا يضمن عدة execute calls على اتصال واحد | فاتورة أو رصيد جزئي | استخدام `Pool::begin` ثم تمرير المعاملة نفسها لكل statements واختبار failure injection |
| المال يمر في float عبر DB أو IPC | اختلاف إجماليات وفروقات قروش | `INTEGER amount_minor`؛ wire money string أو نوع دقيق؛ اختبارات حدية |
| بيع Windows offline وAndroid online على نفس المخزون | بيع زائد أو ازدواج IMEI | نقطة بيع فعالة واحدة وسياسة مزامنة/تسليم معتمدة |
| تحويل مخطط localStorage إلى SQLite | فقدان تاريخ أو رصيد غير مطابق | نسخة أصلية محفوظة، محول idempotent، تقارير مطابقة واختبارات round-trip |
| legacy لا يحتوي كميات إكسسوارات/مستعمل أو باركود/مستخدم منفذ | اختراع تاريخ أو مخزون غير صحيح | لا تخمين؛ جرد افتتاحي يقدمه المالك، barcode enrollment جديد، و`legacy-import` للمنفذ المجهول |
| قواعد الربح وإجمالي المبيعات legacy غير مألوفة | تقارير تاريخية مختلفة | golden fixtures ومعرفات metrics مميزة؛ تغيير الصيغة بموافقة المالك فقط |
| تشغيل بيانات أسعار الجملة على عميل محلي | كشف البيانات لمستخدم له وصول إداري للجهاز | تعريف نموذج التهديد؛ أقل صلاحية، تشفير بيانات حساسة محليًا عند اعتماد السياسة، واختبارات صلاحية |
| عدم مزامنة الصور | صور مفقودة على جهاز جديد | manifest + حزمة صور محلية + placeholders + فحص hash |
| ترخيص مشروع مفتوح المصدر غير متوافق | التزامات نشر/إسناد غير مرغوبة | مراجعة SPDX وترخيص الملف والاعتماديات قبل النسخ أو الدمج |

## نقاط مراجعة بشرية

1. اعتماد capability map وحدود الوحدات.
2. اعتماد المشتريات والموردين في الإصدار الأول.
3. اعتماد طريقة الاستعادة التشغيلية إذا فُقد جهاز Windows وفيه بيانات offline غير متزامنة.
4. اعتماد backend والاستضافة والتكلفة وسياسة الاحتفاظ.
5. اعتماد التشفير المحلي والنسخ الاحتياطي.
6. مراجعة نتائج spike قبل اختيار إطار الواجهة/آلية SQLite النهائية.

## بوابات المراجعة

- بعد المرحلة 1: لا بناء للوحدات قبل اعتماد النطاق ونجاح spike.
- بعد المرحلة 2: مراجعة مخطط البيانات والصلاحيات قبل إدخال بيانات فعلية.
- بعد المرحلة 3: مراجعة البيع offline وسياسة المخزون قبل Android checkout.
- قبل الترحيل: نجاح تجربة الاستعادة والمطابقة على نسخة تجريبية.
- قبل الإصدار: اختبار تثبيت وترقية واستعادة على Windows وAndroid.
