## 1. The owner and the goal

- **Owner:** Peter («بيتر»), runs a mobile-phone shop in Egypt. Writes short Egyptian Arabic («ابدأ»، «كمل»). **Reply in short Egyptian Arabic**: what was done, the evidence, the interpretations taken (numbered, «قولي لو معترض»), how to try it, and the next step ending with «قول "كمل" وأبدأ».
- **Goal:** a sales system for a phone shop that is easy, smart and fast — desktop first (Tauri 2 + Rust + Vue 3 + SQLite, Windows), a companion phone app later (phase 3).
- **Phase 1 acceptance:** one real working day with **zero difference in the drawer and the stock**, and the speed targets: accessory sale ≤ 5 s, IMEI phone with receipt ≤ 15 s, wallet ≤ 8 s, repair intake ≤ 60 s, day close ≤ 3 min, seller switch ≤ 3 s.

## 2. Standing rules from the owner (never break)

- Work in **phases (steps)**; after each: commit, push, CI green, docs, then a **short report**. No build or test claim without a recorded log.
- **Every schema change needs his approval.** The gate approved all phase-1 tables *as proposed* (ADR-016 #31; the proposals are in §6). Anything beyond a proposal goes back to him. Applied migrations are never edited; each change is a new migration.
- **Archive, never delete** (`git mv` into `archive/`, with a line in `archive/README.md`).
- Importing data from the legacy app is banned (ADR-007); taking **ideas** from it is allowed (wallets, phone companies).
- UI: must not look AI-made; two looks («لافتة الشارع», «علبة الموبايل»), light/dark, shop colour from settings, always readable; positions, steps and shortcuts as in the mockup. Only the seller sees the screen.
- Wording: «المخزن» (not «المخزون») everywhere in the UI; «انتظار» (not «تعليق»); «آجل» and «بيّاع» stay.
- Wallet operations never require the customer's number (ADR-016 #27).
- Receipts by WhatsApp only for now (no printer); card, instalments and آجل are optional from settings; commission typed per transaction or from settings; warranty months and receipt footer from settings.
- PIN on every user switch. Sensitive operations need the **owner's PIN** (even on his own session).
- **Never raise the accountant question** («تجاهل موضوع المحاسب»).
- Push only to **`arena/0c9b90ed-system-sales`**; no PR or merge unless he asks.

## 5. Interpretations already told to the owner (he did not object; do not re-ask)

- FIFO positions collapse into an average on first touch; display choices live in the database; any seller may switch the theme.
- 1.1: PIN of 4–6 digits submitted with Enter; one lockout counter shared with the password (5 failures, 15 min); changing a PIN needs the password; «قفل» on the rail; an approval lasts 2 minutes, is spent once inside the operation, survives a refused operation, is replaced by a newer one, and is withdrawn by a PIN change, a disable or a demotion; a locked owner may still use the recovery code; the code alphabet has 31 symbols.
- 1.2 step 1: default categories are renamed, moved and hidden but never deleted; hiding removes the chip only (products stay in «الكل» and search); kind and parent are fixed at creation; names unique across the tree; empty mains still show a chip.
- 1.2 step 2: «موبايل جديد» was moved into step 2; default companies are never deleted; model lines and Arabic spellings live in code; colours wait for 1.4; renaming a company does not rename its phones; the price is required in «موبايل جديد»; search puts names containing the words first.
- 1.2 step 3: «صنف جديد» is now the only way to add a product — the legacy panel's create form was removed and its list/edit/archive stayed; the inline «تصنيف جديد» creates a sub under the chosen counted category's main (a childless main gets its first sub); the shop code is suggested, not reserved, so two screens may be offered the same code and the second save is refused as a used barcode; a typed barcode is 6–14 digits (the mockup's rule); the price is required and above zero; no brand, reorder level, warranty or colour field was added (not in any approved proposal).

## 6. Approved schema proposals not built yet (ADR-016 #31; from the archived handoff §4)

Money is integer piastres throughout. Build each **as proposed**, in its own migration with checks; anything bigger goes back to the owner.

- `products.tracking` = `none | serial_optional | serial_required` (phones default `serial_optional`; the global setting can force `required`).
- `units(id, product_id, imei, imei2, unit_cost_minor, status, received_movement_id, sale_line_id NULL, retired_reason NULL)`, plus `sale_lines.unit_id NULL`; used-device details (grade A/B/C, battery, what comes with it, seller details optional) on the units table (1.4).
- Receipt kind `supplier | opening` (first-time stock, 1.4).
- `sale_payments(sale_id, method, amount_minor, reference NULL)` for split payments, and `customer_ledger` for آجل (1.5).
- Discount limit for sellers, owner PIN above it (1.6).
- `shifts`, `cash_movements`, `expenses` (1.9); `service_entries` (wallet / card / bill / software, `fee_minor` typed per transaction) (1.10); `wallets` (opening, min, max, daily limit, own number, pay method) and `wallet_ops` (deposit, withdraw, top-up/unload via drawer or outside, move, adjust, void with reason) — wallet balances include sales paid by that wallet's method (1.10).
- Partial returns and a `damaged` stock bucket (1.11).
- Settings: `services.fee_mode` (`manual` default | `auto`) with `fee_pct`, `fee_min_minor`, `bill_fee_minor`; `receipt.printer_enabled` (false); `receipt.default_mode`; `payments.enabled_methods`.
- Receipt delivery per sale: channel (`whatsapp | none | print | both`) and the number it was sent to — a column pair on `sales` or a small `sale_receipts` table (1.7).
- `shortages(id, product_id NULL, name, qty, note, customer_name NULL, customer_phone NULL, status open|ordered, created_by, created_at, resolved_at NULL)` (1.15). The sales screen (1.14) reads `sales` + `sale_lines` with indexes, no new table.
- Product variants (parent + values) and `product_images(product_id, file, w, h, bytes)` (1.2 steps 4–5).
- Month reports and registering the used devices already in the shop are **phase 2** (ADR-016 #34).

## 7. How to work in this repository

- **Branch:** `arena/0c9b90ed-system-sales` (no upstream configured: `git push origin arena/0c9b90ed-system-sales`, then check with `git ls-remote`). The previous session's branch, `arena/332710ba-system-sales`, is its history up to `71611b0`; work continues here.
- **No Rust in the sandbox: CI is the only compiler.** `.github/workflows/ci.yml` runs the frontend job (typecheck, unit tests, build) and `cargo test --locked` on Linux for every push; the Windows job (tests + NSIS installer, ~13 min) only when the commit message contains `[windows]`. Read results with `bash scripts/ci-results.sh <run-id>` (raw logs are unreachable). **A push cancels the running job**: wait for it. Re-read new Rust carefully before pushing — every compile error costs a CI round.
- **Frontend:** `npm ci`, `npm run typecheck` (vue-tsc), `npm run test:unit` (node --test on `src/**/*.test.ts`), `npm run build`. Note: `src/env.d.ts` declares `module '*.vue'`, so a missing `.vue` import passes vue-tsc — only the build catches it.
- **Browser demo:** `npm run demo` (0.0.0.0:5173, the in-memory backend in `src/dev/demo-backend.ts` mirrors the Rust rules). Accounts بيتر (owner, PIN 1111), يوسف (2222), مارينا (3333), password 1234; بيتر's recovery code `2345-6789-ABCD-EFGH-JKMN`. Keep the dist free of demo code (scan `dist/` after building).
- **Smoke test:** once `cd docs/ui/mockup-v1/tools && npm ci`; then run `node scripts/demo-smoke.mjs http://127.0.0.1:5173/ /tmp/demo-shots` as a background process and read the log only after its `EXIT` line (82 checks; the recovery checks run last because they change بيتر's password).
- **After a sandbox restart** (it wipes `/tmp`, `node_modules`, processes, and can reset the local branch): `git fetch origin "+refs/heads/arena/0c9b90ed-system-sales:refs/remotes/origin/arena/0c9b90ed-system-sales"`, `git reset --mixed origin/arena/0c9b90ed-system-sales`, `git checkout -- archive/legacy-project/dev_extracted/dist/index.html`, `npm ci` (root, and the mockup tools when needed), restart the preview. Never keep work only in a directory named `dist`, `build`, `out` or `target` (not snapshotted).
- **Docs after each step:** `tasks/todo.md` (the item's «اتعمل/فاضل»), this handoff's §3–§4, `README.md`, `docs/TRY-THE-APP.md`, the ADR's status line, and a learning-log entry at the end of `AGENTS.md` (Egyptian Arabic). Edit with small Python scripts that assert each anchor occurs exactly once. Never rewrite line-cited docs (`docs/superpowers/specs`, `docs/superpowers/plans`, ADR-008, ADR-013) or applied migrations.
- **Code conventions:** Rust layers — `domain` (no SQL/Tauri), `data/repositories` (all SQL), `services` (authorise → one transaction → audit → commit), `commands` (transport only; never a token/role/actor/user_id parameter). Stable error codes, each with an Arabic message in `src/api/errors.ts` (the architecture suite checks both directions). Audit details built with `serde_json`. Pure frontend logic in `*.ts` with `*.test.ts` beside it.
- **Architecture guards that trip often:** ban lists scan comments too; the three tests pinning the migration ledger (`products_profile_migration`, `migration_backward_compat` ×2) must move with each new migration; command registrations are pinned in `every_authority_command_is_registered_in_lib`; services must hold no SQL; sqlx takes SQL as `&'static str`.
